# 금손한의원 블로그 자동화

금손한의원 박준희 원장이 환자 한 명에게 직접적이고 분명하게 설명하는 정보 글을 만든다. 부드러워 보이게 하려고 뜻을 흐리거나 추상어로 압축하지 않는다. 내부 기획 라벨, 레퍼런스 ID, SEO 횟수, 검수표, 이미지 지시는 완성 본문에 노출하지 않는다.

글은 기존과 같이 `clinic-info 운영정보 표에서 끝`내며, 다중 정보 수집은 보이는 글 구조를 추가하거나 바꾸지 않는다.

## 시작 브리핑과 자동화 버전

- 현재 자동화 버전: `1.27`
- 현재 버전 브리핑: 시작할 때 정보형 주제 10개를 번호로 추천하고 사용자는 번호를 고르거나 원하는 주제를 직접 입력할 수 있다. 주제와 메인키워드가 모이면 제목 5개를 먼저 빠르게 제안하고, 확정 제목 뒤 관련 자료를 조사한다. 사용자가 지정한 주제는 최근 글과 같거나 비슷해도 그대로 작성하며 최근 이력으로 거절·변경하지 않는다. 본문은 사용자가 선택한 v1.13 원고의 자연스러운 문단 호흡과 충분한 설명 흐름을 따르며, 이후 버전의 문장 수·문단 수 강제 제한은 적용하지 않는다.
- 이 스킬이 활성화되면 주제 추천·선택, 메인키워드 질문, 제목 추천·선택, 작업 설명, 도구 실행보다 먼저 아래 두 문장을 사용자에게 보인다. 전역에서 요구하는 스킬 사용 안내가 필요할 때도 이 두 문장 자체를 사용하며, 그보다 앞에 별도 안내를 붙이지 않는다.

  `금손한의원 블로그 자동화 v{현재 자동화 버전}을 시작합니다.`

  `현재 버전: {현재 버전 브리핑}`
- 중괄호를 그대로 출력하지 않고 위의 관리 값으로 치환한다. 패키지용 세 자리 SemVer, `+codex` 캐시버스터, 소스 지문은 사용자에게 노출하지 않는다.
- 사용자가 선택하는 실행 모드는 없다. 항상 자동 작성으로 진행하며 모드 선택 메뉴를 출력하지 않는다. 두 문장 뒤에는 `주제 10개 추천 → 추천 번호 선택 또는 주제 직접 입력 → 메인키워드 → 제목 5개 추천 → 추천 번호 선택 또는 제목 직접 입력` 순서로 진행하고, 확정 제목을 받은 뒤 나머지 글을 자동 작성한다. 사용자가 처음부터 주제를 주면 주제 추천 단계는 건너뛴다.
- 현재 버전의 단일 기준은 `assets/automation-version.json`이다. 플러그인 소유자가 스킬·스크립트·레퍼런스·자산·플러그인 구성을 실제로 바꾼 뒤 `scripts/refresh_plugin.py`를 실행하면 기능 소스 지문이 달라진 경우에만 `1.0 → 1.1 → 1.2`처럼 마이너 버전을 한 번 올리고, 이 SKILL의 관리 값과 플러그인 패키지 버전을 함께 맞춘다. 같은 내용을 검증·설치·배포 때문에 다시 실행할 때는 버전을 올리지 않는다. 버전 값은 수동으로 고치지 않는다.

## 운영체제별 실행기

- 플러그인은 macOS와 Windows에서 같은 글쓰기·검수·HTML 계약을 사용한다.
- Python 명령은 현재 운영체제에서 실제로 종료 코드 0으로 실행되는 Python 3 실행기를 먼저 확인한다. Windows에서는 한글 JSON 출력을 보존하도록 `py -3 -X utf8`, 다음으로 `python -X utf8`을 사용한다. macOS 공유 설치본에서는 먼저 `${CODEX_HOME:-$HOME/.codex}/state/goldhand-clinic-blog/bin/python3`, 다음으로 `python3`을 사용한다. 아래 예시의 `python3`는 이렇게 확인한 실행기로 치환한다.
- Windows 출력 폴더는 레지스트리에 등록된 실제 바탕화면을 우선 사용하므로 OneDrive 바탕화면도 따른다. 복사 안내는 Windows에서 `Ctrl+V`, macOS에서 `⌘V`로 표시한다.
- GPT Image 생성·본문 배치는 두 운영체제에서 동일하다. 설명 이미지는 시스템 `$imagegen`을 명시적으로 호출하고 내장 `image_gen` 모드로만 생성한다. `scripts/image_gen.py`·CLI/API 대체 경로는 사용하지 않으며 `OPENAI_API_KEY`를 묻거나 확인하거나 저장하지 않는다. 내장 도구가 현재 작업에 없으면 이미지 없는 불완전 HTML이나 API 키 안내를 만들지 말고, 최신 ChatGPT 데스크톱 앱의 새 작업에서 `$imagegen` 단독 생성을 먼저 확인하라고 알린 뒤 중단한다. 공유용 설치기는 필요한 Node.js와 Vercel CLI를 자동으로 준비한다. 최초 설치 또는 첫 글에서 이미지 호스트 설정이 없으면 `scripts/setup_image_host.py`를 실행한다. 사용자는 코드가 자동 적용되어 열린 브라우저에서 본인 Vercel 로그인과 Allow만 승인한다. 코드를 찾거나 직접 입력하게 하지 않으며, 코드 없는 일반 인증 주소를 열지 않는다. 프로젝트 생성·연결·첫 배포·고정 공개 주소 선택·`image-host.json` 저장은 스크립트가 맡고, 만료된 승인 요청은 새 요청으로 한 번만 자동 교체한다. Vercel 토큰·일회용 코드·완성 승인 주소·계정 정보는 플러그인 설정이나 대화에 넣지 않는다. 네이버가 읽을 공개 HTTPS 주소로 게시할 때 Windows에서는 npm의 `vercel.cmd`·`vercel.exe`·`vercel` 순서로 실제 실행 파일을 찾는다. macOS에서는 `${CODEX_HOME:-$HOME/.codex}/state/goldhand-clinic-blog/bin/vercel`을 먼저 확인한 뒤 `vercel`을 사용한다.
- 플러그인 소유자가 이 스킬·스크립트·레퍼런스·자산·플러그인 구성을 수정한 작업에서는 전체 검증 뒤 플러그인 루트의 `scripts/refresh_plugin.py`를 실행한다. 이 명령이 기능 소스 지문을 기준으로 자동화 버전을 필요할 때만 한 번 올린 뒤 설치본을 갱신한다. 소유자 전용 `publisher.json`이 자동 배포를 켠 환경에서는 완전한 원본 동기화, GitHub 푸시, Windows CI 성공 확인, 새 Release와 두 공개 자산의 SHA-256 검증, 공개 설치 테스트까지 끝내야 완료다. CI나 공개 자산 검증이 실패하면 배포 완료라고 보고하지 않는다. 사용자 설치 환경에는 소유자 GitHub 권한이나 배포 설정을 만들거나 요구하지 않는다.

## 절대 계약

1. 작성 형식은 정보 본문형 하나뿐이며 HTML 유형 값은 `정보전달형`이다. 일상글은 말투 분석 자료일 뿐 생성하지 않는다.
2. 도입의 대표 독자 고민은 확정 주제·제목과 선택한 편집 마스터의 질문 기능을 금손 내용으로 바꿔 2~3개 둔다. 이 질문 2~3개를 글의 첫 보이는 문장으로 연속 배치한 뒤에만 고정 인사를 쓴다. 같은 뜻을 늘려 개수를 맞추지 않는다.
3. 마지막 고민 뒤, 첫 정보 소제목 전에 제목이 약속한 답을 한두 문장으로 먼저 단정한다. `이번 글에서는`, `세 가지를 알면`, `읽고 나면`, `설명하겠습니다`처럼 글의 진행이나 독자의 보상을 예고하지 않는다. 이 부분은 환자가 지금 무엇을 하지 말아야 하는지, 금손이 무엇을 묻고 왜 묻는지를 바로 말하는 배경·테두리 없는 일반 산문 문단으로 쓴다.
4. 업체소개형·사례공유형·스토리텔링형·일상글·공지·이벤트는 자동 선택, 최근 이력 회전, 무작위 선택, 기본값, 자료 부족 fallback 어디에도 넣지 않는다.
5. 글 주제가 아직 없으면 `assets/topic-recommendation-contract.json`과 `assets/beomeo-topic-idea-library.json`의 `autoEligible=true`인 `topicIdeas[].topicIdea`만 사용해 서로 다른 정보형 주제를 정확히 10개 번호로 추천한다. 최근 글 이력·일반 정보 자산·편집 마스터·웹 자료는 이 단계에서 읽지 않고, 최근 글과의 유사성을 추천 제외·교체 근거로 쓰지 않는다. 사용자가 1~10번을 고르면 해당 문구를 그대로 주제로 확정하고, 번호 대신 원하는 주제를 입력하면 그 문구를 실제 글 주제로 고정한다. 최근 완료 글과 주제·대상·검색 의도·동의어가 같거나 비슷해도 거절·변경·보류하지 않고 사용자가 지정한 주제로 작성한다. 최근 글 이력은 공식 사진 순환과 완료 기록에만 사용하며 주제·제목·본문 각도를 차단하거나 대체하는 근거로 쓰지 않는다. 제목이 확정된 뒤에만 `scripts/select_general_information.py`로 `assets/wipark-content-briefs.json`과 `assets/user-general-information-references.json`의 관련 글 여러 편에서 일반 정보 원자를 모으고 의미 중복을 제거한다. 저장 정보가 없거나 확정 제목의 답을 충분히 채우지 못해도 다른 주제를 요구하거나 임의 주제로 바꾸지 않는다.
6. 저장 정보가 부족하면 `scripts/search_naver_background.py`로 주제를 한국어로 네이버 검색하고 `scripts/fetch_naver_post_text.py`로 후보 본문을 임시 읽는다. 이 검색은 Windows·macOS에서 브라우저 GUI·로그인·사용자의 현재 브라우저 상태에 의존하지 않는다. 서로 다른 발행자 2곳 이상을 비교하고 치료·검사·안전 설명에는 한국 공식 의료 출처를 하나 이상 포함한다.
7. 콘텐츠 정보 출처와 편집 마스터를 분리한다. 제목 확정 전에는 편집 마스터를 고르지 않는다. 확정 제목 뒤 일반 정보는 여러 관련 글에서 합치고, 기존 글 구조는 `scripts/select_reference_master.py`가 확정 제목과 주제로 고른 `referenceWritingIntelligence` 한 편의 `flowBeats`·제목 심리·도입 설득·전환·마무리 감정만 따른다. 콘텐츠 출처가 늘어나도 도입·소개표·본문·마무리·이미지·운영정보·HTML 순서를 바꾸지 않는다.
8. 저장 레퍼런스의 `orderedContentAtoms`는 여러 출처를 합치기 전의 정보 원자일 뿐이며, 의미 중복을 제거한 `mergedInformationAtoms`를 본문 사실 골격으로 사용한다. 모든 출처의 완성 문장, 7어절 이상 연속 표현, 업체명·지역·원장·경력·환자 수·성과·사례·프로그램·장비·처방 구성·가격·사진·연락처·내원 유도는 가져오지 않는다. 출처별 차단 엔터티를 기록하고 `validate_information_sources.py`로 완성 본문 누출을 막는다. 금손한의원·박준희 원장·진료·운영 정보는 오직 `references/clinic-facts.md`에서만 삽입한다.
9. 꾸밈은 편집 마스터와 무관하게 `goldhand-naver-native-v4`로 고정한다. 네이버 순정 인용구·구분선·표1 외의 CSS 카드, 둥근 박스, 그림자, 왼쪽·위쪽 강조선, 1행×1열 가짜 표는 쓰지 않는다.
10. 인용구 2~3개는 실제 환자 발화라고 주장하지 않는다. 확인된 직접 인용이 아니라 검색 독자를 대표하는 고민으로 쓴다.
11. 기본 화자는 박준희 원장이다. 글은 대표 독자 고민 인용구 2~3개로 바로 시작하고, 그 다음에 `안녕하세요, 금손한의원 박준희 원장입니다.`를 정확히 한 번 쓴다. 인사·병원명·원장 소개를 첫 질문보다 앞에 두거나 질문 사이에 끼우면 실패다.
12. 이모지, `^^`, `ㅎㅎ`, `ㅠㅠ`, 하트, 해시태그 장식, 강한 내원 유도, 치료 보장을 쓰지 않는다.
13. 예시 금지어만 피해 비슷한 문장으로 바꾸지 않는다. `조금 더 분명히 구분할 수 있습니다`, `차분히 살펴보겠습니다`, `구체적인 단서가 될 수 있습니다`를 포함해 번역투 명령문, 독자에게 기록·관찰·정리를 숙제처럼 시키는 문장, 감성적 여운을 위한 추상 결론을 만드는 생성 방식 자체를 쓰지 않는다. `판단·기준·구분·확인`은 실제 동작보다 많이 반복하지 않는다.
14. 문법적으로 자연스러운 것만으로 통과시키지 않는다. 지나치게 완곡하게 돌려 말하는 안내, 독자에게 교훈을 주거나 여운을 남기는 결말, 실제 대화보다 블로그 작문을 위해 만든 티가 나는 문장도 실패다. `아픈 자리`, `걷기가 달라지다`, `자세가 이어지다`, `부담이 반복되다`, `치료 방향에 차이를 만들다`처럼 추상 명사에 작문용 서술어를 붙인 압축 표현도 같은 원리에서 모두 제거한다. `아픈 곳`, `평소보다 걷기 힘들다`, `같은 자세로 오래 일하면 목이 다시 뻐근하다`처럼 환자가 듣자마자 동작과 불편을 떠올릴 수 있는 생활어로 문장 구조부터 다시 쓴다.
15. 완성물은 항상 `제목 + 본문 + 네이버 복사용 HTML`이다. 사용자가 HTML을 명시적으로 제외한 경우에만 파일을 생략한다.
16. 인용구·인사·해결 방향·소제목·일반 본문·표를 포함한 모든 글은 중앙 정렬한다. 왼쪽 정렬을 섞지 않는다.
17. 핵심 결론에는 노란 하이라이트 정확히 3개, 실제로 필요한 구체적 행동에는 네이버 순정 밑줄 2~3개, 중단·검사·주의 같은 안전 경계에는 빨간 글씨 1~2개를 넣되 합계는 6~8개다. 밑줄 개수를 맞추려고 기록·관찰·회상 숙제를 만들지 않는다.
18. 가치입증은 후보나 주제별 선택이 아니다. `assets/goldhand-value-proof-library.json`의 고정 6행을 모든 글에서 같은 문구·순서로 사용한다.
19. `금손한의원 소개` 가치입증 표는 모든 글에서 도입 질문·인사·`solution-preview`가 모두 끝난 뒤, 첫 정보 본문의 구분선·소제목·설명보다 앞에 둔다. `before-credential` 배치를 선택했을 때만 `solution-preview`와 표 사이에 실제 사진 1장을 허용하며, 그 밖의 본문·이미지·표는 끼우지 않는다.
20. 글 주제와 메인키워드가 모이면 리서치·레퍼런스 탐색·최근 글 이력 확인·편집 마스터 선택보다 먼저 `assets/title-recommendation-contract.json`만 사용해 서로 다른 제목을 정확히 5개 만든다. 사전 JSON은 `workflowStage=title-first`이며 `referenceMasterId`와 `titleMechanismId`를 넣지 않는다. 모든 추천 제목은 정확 메인키워드로 시작하고 공백 제외 30자 이내이며, 독자가 얻을 이득 또는 피할 손해가 바로 보이는 `최악의·반드시·망치는·놓치면 손해·경고하는` 같은 강한 표현을 쓴다. 각 후보는 확인된 `11년차` 또는 `1가지·2가지·3가지` 숫자 장치 중 하나 이상을 사용한다. 다섯 개 중 `11년차` 후보는 최소 1개, 1~3가지 답 개수 후보는 최소 3개다. 위석의 경력·환자 수·원장 수는 버린다. 사용자가 제목을 고른 뒤에만 관련 자료를 조사하고, 숫자 약속과 같은 개수의 서로 다른 실제 답을 확보·검증한다. 답을 확보하지 못하면 제목을 임의 수정하지 않고 새 제목 선택만 요청한다.
21. `solution-preview`에는 `data-intro-persuasion-device`와 보이는 `data-reader-payoff`를 둔다. `specific-number-low-friction-topic-payoff`를 선택한 경우에만 `reading-time-hook`을 한 번 쓰고, 실제 분량에 맞는 1~5분의 숫자와 제목·독자 고민에 직접 연결되는 보상을 함께 제시한다. 3분을 모든 글에 반복하거나 숫자 뒤에 막연한 도움만 약속하면 실패다.
22. 도입에서 오십견 핵심 또는 독자의 불편을 설명하는 한 구절을 노란색으로 표시한다. 노란 하이라이트 3개 가운데 1개는 반드시 `solution-preview`에, 나머지 2개는 서로 다른 본문 구간에 둔다.
23. 시각 자료는 사용자가 본인 소유라고 확인한 [네이버 OGQ마켓 callilife](https://ogqmarket.naver.com/creators/callilife?type=STOCK_IMAGE)에서 주제와 직접 맞는 작품 3~4개를 찾는다. 작품마다 시스템 `$imagegen`을 명시적으로 호출하고 내장 `image_gen`을 한 번씩 별도로 사용한다. 인물 중심 그림은 동작·자세·구도·화살표·각도·표기·그림체를 유지하고 얼굴형·이목구비·헤어·피부색·의상 색이나 디테일 가운데 2~3개만 미세하게 바꾼다. 비인물 중심 그림은 핵심 사물·정보·구도·표기를 유지하고 선 굵기·채색·명암·질감 가운데 1~2개만 살짝 바꾼다.
24. 원고 article에는 OGQ 미리보기나 원본을 넣지 않고 GPT Image 생성본의 절대 로컬 경로만 넣는다. 빌드할 때는 생성본을 금손 전용 HTTPS 이미지 호스트에 게시하고, 청년통신 복사 페이지와 동일하게 공개 HTTPS 주소를 `<img src>`와 `data-reference-source-url`에 넣는다. 네이버가 제외하는 `data:image/...;base64`는 만들지 않는다. 실제 진료 사진·마무리 신뢰 사진·GPT 이미지 모두 `<figcaption>`이나 이미지 아래 설명 문단을 만들지 않는다. 작품 상세 URL·사용자 소유 확인·의학 정보 및 배치 보존·허용된 변형 모드는 보이지 않는 검수용 `data-*`와 `alt`에만 남기며 네이버 복사 본문에서는 내부 `data-*`를 제거한다. 인물 중심 그림의 그림체 변경, 비인물 중심 그림의 내용·배치 변경은 실패다. 구매·가격 확인·라이선스 요청 단계는 없다.
25. 생성한 이미지는 별도 첨부로 끝내지 않고 최종 `<article>`과 네이버 복사용 HTML 안에 반드시 삽입한다. 각 이미지는 그 그림이 직접 설명하는 증상·동작·치료 원칙을 적은 모바일 문단 바로 뒤에 한 장씩 둔다. 3~4장 모두 원장 소개표 뒤 첫 두 개 설명 섹션 안에 배치하고, 그중 최소 1장은 첫 번째 설명 섹션에 둔다. 각 figure에는 `data-image-zone="early-explanatory-body"`를 표시한다. 세 번째 설명 섹션 이후, 도입과 본문 사이, 소제목 직후, 관련 없는 문단 뒤, 글 끝에 몰아넣는 배치는 금지한다. `<figure>`에는 `data-image-placement="after-related-paragraph"`와 직전 문단에서 실제로 확인되는 `data-image-anchor`를 둔다.
26. GPT Image 3~4장과 별도로 실제 **진료 사진**은 두 배치 중 하나만 사용한다. `before-credential`은 해결 방향 예고 뒤·`금손한의원 소개` 표 바로 위에 정확히 1장, `closing-trust`는 `neutral-close` 뒤의 마지막 신뢰 구간에 정확히 2장이다. 진료 사진을 설명 본문 중간에 분산하거나 두 배치를 섞으면 실패다. 공식 블로그에서 수집한 113장 전부는 플러그인 `assets/official-media`에 들어 있으며, `assets/media-library.json`에서 진료 사진으로 `safeAuto: true`이고 번들 파일·해시가 확인된 6장만 이 수량에 사용할 수 있다. 사용자 바탕화면이나 개인별 사진 폴더를 요구하지 않는다.
27. 실제 사진은 `원장이 환자를 치료하는 장면 → 원장이 환자를 진찰·상담·설명하는 장면 → 원장이 환자를 검사하는 장면`만 선택한다. `personInteraction: true`, `directorVisible: true`, `sceneType: director-patient-*`를 모두 충족해야 한다. 금손한의원 로고·간판·건물 외부·약·환제·탕약·장비·제품·빈 원내 공간은 수량이 부족해도 절대 fallback으로 쓰지 않는다. `before-credential`은 바로 직전 완료 글과 다른 사진만 쓰고, `closing-trust`는 다른 사진을 우선하되 두 장을 채우지 못하면 직전 글의 시각 검수 승인 사진을 재사용한다.
28. 진료 사진과 **별도로**, 시각 검수된 원장·협약·수료증·기부·봉사 장면을 글마다 정확히 1장 더 사용한다. `recommend_closing_trust_media.py`로 `closingTrustEligible: true`인 7장 중 직전 완료 글과 겹치지 않는 사진을 고른다. `neutral-close`와 필요한 마무리 산문 뒤, 진료시간 안내 앞에 `data-trust-photo="true" data-trust-photo-slot="closing-credential-trust"`로 두며 진료시간 전 마지막 이미지여야 한다. 이 사진은 진료 사진 1장/2장 수량에 절대 포함하지 않는다.
29. `before-credential` 진료 사진은 `placementTerms`·`approvedAlt`를 정확히 사용하고 바로 앞 문단과 `data-image-anchor`가 같은 승인 장면을 가리켜야 한다. `closing-trust` 진료 사진 2장은 질환·부위·본문 문맥과 맞지 않아도 되며, `data-image-placement="closing-clinical-gallery"`로 두고 `data-image-anchor`나 관련 문단을 요구하지 않는다. 다만 자산의 정확한 `approvedAlt`는 유지한다. 별도 마무리 신뢰 사진은 정확한 `closingTrustApprovedAlt`·원본 URL·ID·SHA256을 유지하고 `data-image-placement="closing-credential-trust"`로 단독 배치한다. 이 사진 앞뒤에 협약·수료·기부·봉사 장면을 설명하는 보이는 문장, `credential-trust-context` 문단, `<figcaption>`을 만들지 않는다. 환자·가족 얼굴, 이름, 연락처, 차트, 처방전, 검사결과가 식별되거나 시각 검수를 통과하지 않은 사진은 사용하지 않는다.
30. `before-credential`의 문맥 일치 승인 사진 1장을 고르지 못하거나, 시각 검수된 실제 진료 사진 풀 자체가 `closing-trust` 2장에 못 미치거나, 별도 마무리 신뢰 사진 1장을 고르지 못하면 자동 작성 중에도 HTML 조립과 발행을 중단한다. `closing-trust`에서는 주제 불일치나 직전 글 사용 이력만으로 중단하지 않고 승인 사진을 재사용해 정확히 2장을 넣는다. 두 사진 풀은 서로 대체하지 않는다.
31. 모든 글의 고정 운영정보는 공휴일 행이 없는 `clinic-hours` 진료시간 3열 표 다음, 위치·찾아오는 길·전화만 담은 `clinic-info` 1열 다행 표 순서로 둔다. 카카오톡·네이버 예약은 출력하지 않는다. 글은 `clinic-info` 표에서 끝내며, 그 뒤에는 `<함께 보면 좋은 글>` 문구, 최신 블로그 글 링크·카드, 네이버 지도·장소 컴포넌트, 해당 자리표시자를 넣지 않는다.
32. 정보 본문 뒤에는 `neutral-close`를 정확히 한 번 둔다. 내부 순서는 `글별 마무리 소제목 → 순정 구분선 → 가장 중요한 판단 한 문장 → 불편이 계속될 때의 부담 없는 진료 안내 한 문장`이다. 번호 답 전부를 다시 요약하거나 첫 번째·두 번째·세 번째라고 계산하지 않는다. 소제목은 제목·증상·본문 결론에 맞춰 매번 새로 쓰며 `25년 경험이 전하는 한 가지`, `오늘의 결론`, `마무리` 같은 고정 공식으로 만들지 않는다. 진료 안내는 예약을 재촉하거나 결과를 약속하지 않고, 어떤 시간·동작에서 어느 부위가 계속 아플 때 무엇을 진료할지 직접 말한다.
33. 완성 산문과 정확 키워드 배치가 끝나면 기본적으로 [references/final-writing-voice-review.md](references/final-writing-voice-review.md)를 읽고 `writing-voice-final-rehear-v1` 최종 재청취를 실행한다. 사용자가 동일 공통 원고의 A/B 윤문 비교를 명시한 경우에만 이 검수 직전 원고를 두 벌로 복제해 A안은 writing-voice, B안은 [references/final-humanize-korean-review.md](references/final-humanize-korean-review.md)의 `humanize-korean-final-pass-v1`을 적용한다. B안에서는 writing-voice나 A안 수정 결과를 사용하지 않는다. 어느 경로든 내용 추가·삭제·순서 변경, 사실·의료 경계·확신 강도·제목·도입·흐름·마무리 장치 변경, SEO 약속·고정 HTML 구성 변경은 금지한다.

### 사용자 확정 직설 원장체

이 규칙은 모든 정보글의 평문 초안, 독립 발화 편집, 최종 윤문에 항상 적용한다. 사용자가 매번 별도 프롬프트로 다시 요청하게 하지 않는다. [v113-approved-writing-style.md](references/v113-approved-writing-style.md)를 최상위 글쓰기 호흡 기준으로 읽고, 목표는 문장만 매끈하게 다듬는 것이 아니라 박준희 원장이 환자에게 직접 설명하듯 **누가 무엇을 하고 왜 그렇게 하는지 한 번에 알아듣게 쓰는 것**이다.

- 추상적이고 압축된 AI 문장을 만들지 않는다. `잠 밖에 있습니다`, `치료의 출발점입니다`, `몸의 흐름을 봅니다`, `회복의 방향을 찾습니다`, `설명도 이어집니다`처럼 실제 행동과 뜻이 보이지 않는 문장은 실패다.
- 금손의 진료 방식이나 판단을 설명하는 문단은 `저희 동천동 한의원 금손한의원에서는`, `저희 금손한의원에서는`, `저는 진료할 때`처럼 주체를 먼저 밝힌다. 모든 문장에 상호를 기계적으로 반복하지 말고, 하나의 설명 단위에서 누가 행동하는지 분명해야 한다.
- 짧고 그럴듯하게 압축하지 않는다. 원문이 한 문장으로 뭉뚱그려져 있으면 `분명한 결론 → 실제로 묻거나 확인하는 내용 → 그렇게 하는 이유나 목적`을 두 문장까지 풀어 쓴다.
- 문장은 `주체 → 실제 진료 행동 → 이유·목적`의 관계가 보이게 쓴다. 모든 문장을 똑같은 세 토막으로 만들라는 뜻이 아니라, 어느 요소도 추상어로 숨기지 말라는 뜻이다.
- 질문을 한 줄씩 나열해 문진표처럼 만들지 않는다. 다만 번호 답 하나에 필요한 질문·진찰·검사·생활수칙·치료 판단은 설명 흐름상 필요하면 여러 문단에 충분히 쓸 수 있다. 항목 수를 줄이기보다 질문 뒤에 왜 묻는지와 판단이 어떻게 달라지는지를 자연스럽게 이어 쓴다.
- 문장 길이, 쉼표 수, 문단별 문장 수를 숫자로 제한하지 않는다. 보통 두세 문장이 한 문단으로 읽히는 v1.13 호흡을 참고하되, 한 문장으로 끝나거나 세 문장 이상 이어지는 편이 자연스러우면 그대로 둔다. 숫자에 맞추려고 내용을 삭제하거나 한 문장에 압축하지 않는다.
- 번호 답 하나를 두 문단·네 문장으로 잘라 끝내지 않는다. 환자가 겪는 장면, 원인, 진료에서 묻는 내용, 안전 기준, 치료 판단을 독자가 이해할 만큼 설명하고 다음 번호로 넘어간다.
- `solution-preview`는 제목이 약속한 결론을 먼저 분명하게 말한다. 길이를 맞추는 대신 번호 본문과 자연스럽게 이어지게 쓰고, `첫째·둘째를 살펴보겠습니다` 같은 글 진행 안내는 넣지 않는다.
- 같은 질문이나 진찰 장면도 도입에서 문제를 꺼내고 본문에서 이유를 설명하거나 마무리에서 안전 행동을 다시 강조할 필요가 있으면 되짚을 수 있다. 똑같은 문장을 분량 채우기로 복사하는 것만 피한다.
- 독자에게 `고개를 돌려 보세요`라고 직접 말해도 되고, `저는 환자에게 고개를 돌려 보게 합니다`처럼 진료 과정을 설명해도 된다. 어느 방식이든 실제로 움직이는 사람, 묻는 사람, 보는 사람이 분명하고 한국어 입말로 자연스러우면 통과한다.
- `그런데·그래서·다시·따로·이어`는 실제 대조·원인·반복·분리가 있을 때만 쓴다. 연결어를 지워도 뜻이 같거나 앞 문장에 근거가 없으면 삭제한다.
- 첫 진료·치료 직후·다음 날·다음 방문의 시점을 섞지 않는다. 미래의 증상은 지금 이미 물었다고 쓰지 말고, 무엇을 기록해 다음 진료 때 보여 줄지 말한다. 결과지는 `가져오세요`, 약 사진은 `찍어 오세요·보여 주세요`라고 쓴다.
- 원문의 판단이 단정적이면 `절대`, `반드시`, `샅샅이`, `근본적인 원인`처럼 독자가 바로 이해하는 강도를 필요한 곳에 그대로 쓴다. 다만 원문과 의학 정보가 가능성만 말하는 곳을 새로 단정하거나 치료 결과를 보장하지 않는다.
- `~할 수 있습니다`, `~해볼 수 있습니다`, `살펴보셔도 좋습니다`, `도움이 됩니다`, `한 가지 출발점입니다`처럼 뜻을 흐리는 완곡어를 관성적으로 쓰지 않는다. 실제 뜻이 금지라면 `하시면 안 됩니다`, 필수라면 `확인해야 합니다`, 결론이라면 `절대 알 수 없습니다`처럼 직접 말한다.
- 핵심 증상과 행동은 `이것·그 부분·이런 흐름`으로 숨기지 않는다. `몇 시에 잠드는지`, `밤에 몇 번 깨는지`, `다시 잠들기까지 얼마나 걸리는지`처럼 환자가 겪는 장면을 그대로 말한다.
- `상태·변화·반응·방향·기준·순서·과정·양상·흐름·신호·움직임·생활·모습·단계`를 쓴 문장은 전부 다시 읽는다. 같은 문장 안에서 구체적인 시간, 동작, 신체 부위, 증상, 실제 질문이나 조치가 보이지 않으면 그 추상 명사를 삭제하고 구체적인 말로 다시 쓴다.
- `solution-preview`와 `neutral-close`도 예외가 아니다. `말씀드리겠습니다`, `현재 상태를 함께 살펴보겠습니다`, `치료 순서의 문제입니다`, `두 가지를 기억하세요`처럼 글의 진행이나 추상 결론을 말하지 않고, 독자가 실제로 무엇을 하지 말아야 하는지 또는 진료에서 무엇을 묻는지를 바로 쓴다.
- 쉬운 낱말만 쓴 문장도 입으로 다시 읽는다. `붓기가 커지다`, `두통이 덜 오다`, `근력과 균형이 돌아오다`, `발목이나 다리에 힘이 들어오다`, `진료에서 말씀하다`, `무리하지 않는 운동`, `병원 검사가 급하지 않다`, `먹고 언제 더부룩한지`처럼 뜻은 알아도 실제로는 잘 말하지 않는 결합은 실패다. `붓기가 심해지다`, `두통이 덜 생기다`, `한 발로 서도 발목이 흔들리지 않다`, `다친 쪽 다리로 몸을 지탱할 수 있다`, `진료할 때 말씀하다`, `가볍게 운동하다`, `병원 검사를 먼저 받아야 할 증상이 없다`, `식사 뒤 언제부터 더부룩한지`처럼 환자가 해 볼 수 있거나 원장이 볼 수 있는 장면으로 문장 구조부터 고친다.
- 통증·저림·당김·메스꺼움은 환자에게 `묻습니다`. 원장이 몸을 누른 뒤에도 `아픈 곳을 확인합니다` 또는 `어디가 아픈지 봅니다`라고 쓰지 않는다. `복숭아뼈 주변을 누른 뒤 어디가 아픈지 묻습니다`라고 행동과 답의 주체를 나눈다.
- `안 아픈 척`은 환자가 일부러 통증을 숨겼다는 사실이 있을 때만 쓴다. 사고 직후 실제로 안 아팠던 장면은 `사고 직후 안 아파도 그냥 넘기지 마세요`라고 쓴다.
- 치료 판단을 `침 치료만 권해도 된다면`처럼 허가 표현으로 우회하지 않는다. `치료할 곳을 고릅니다`, `한의 치료를 시작할 수 있는지 설명합니다`, `침 치료만 설명합니다`, `침이나 추나요법이 필요하다면 왜 쓰는지 설명합니다`처럼 치료 행정만 보고하지도 않는다. 실제 부위·진찰 결과·권하는 치료를 직접 말한다.
- `그 답을 들은 뒤`, `제가 묻는 질문도 달라집니다`, `진료실에서 물어볼 내용이 다릅니다`, `두 질문부터 해야 하죠`처럼 문진 절차를 이유로 쓰지 않는다. 답 때문에 실제 진료 판단이 어떻게 달라지는지 말한다. `필요하지 않다면 함께 권하지 않습니다`, `모든 증상에 같은 치료를 권하지 않습니다`처럼 치료 목록으로 병원의 태도를 방어하지 않는다.
- 환자에게 행동을 지시할 때는 같은 청자에게 말하되, 명령을 연달아 읽지 않는다. 판단과 이유를 먼저 말한 뒤 꼭 필요한 지시 한두 문장만 둔다.
- 한 문장에 문진·눈으로 보는 동작·누르는 진찰·치료 판단을 세 가지 이상 이어 붙이지 않는다. 행동마다 문장을 나눠 실제 진료 장면이 바로 들리게 쓴다.
- 환자의 불편을 말할 수 있는데 `위에서 음식이 천천히 내려가다`, `위가 조금만 늘어나다`처럼 장기 작동을 추정해 대신 설명하지 않는다. 몇 숟갈 먹었을 때 배가 차는지처럼 환자가 실제로 겪는 장면을 쓴다.
- 정확 키워드는 반드시 `저희 {정확 메인키워드} 금손한의원에서는`이라는 한 문장 안에 둔다. `광주 ○○ 한의원에 오실 때는 …` 다음에 `저희 금손한의원에서는 …`을 따로 쓰는 분리형은 키워드 횟수가 맞아도 실패다.
- 앞에서 나열한 항목 수와 뒤의 `이 두 행동·세 가지·각각`이 정확히 맞아야 한다. 세 행동을 적고 두 행동이라고 받으면 문법이 자연스러워도 실패다.
- 시간·거리·음식·증상처럼 종류가 다른 목적어를 `듣습니다` 하나에 묶지 않는다. `다친 시각과 걸을 수 있는 거리를 들은 뒤`, `병원 진료부터 말씀드립니다`, `탄산음료 뒤에`처럼 뜻만 짐작되는 문장은 각각 실제 질문·권유·섭취 행동을 밝혀 다시 쓴다. 기본 동사와 오탈자도 소리만 비슷하다고 통과시키지 않는다.
- `허벅지에 힘이 들어가다`처럼 힘을 추상적으로 쓰지 않는다. 계단에서 허벅지가 떨리는지, 몸이 한쪽으로 기우는지처럼 환자가 하거나 원장이 볼 수 있는 동작을 쓴다.
- `사고가 난 시각과 통증이 시작된 날부터 묻습니다`, `잠·끼니·커피 가운데 언제 더부룩했는지`처럼 서로 다른 시간 단위와 생활 습관을 하나의 질문에 묶지 않는다. 직접 연결된 질문은 한 문장에 두 개까지만 두고 나머지는 나눈다.
- `병원 진료부터 권합니다`, `영상검사를 받을 수 있는 병원 진료`, `말하고 치료합니다`, `다른 병원 진료를 권합니다`처럼 명사와 조사를 겹쳐 실제 안내·설명·치료 순서를 숨기지 않는다.
- `환자의 답을 들은 뒤 … 살핍니다`, `빼놓지 않습니다`, `빠뜨리시면 안 됩니다`로 다음 질문이나 환자의 말하기 행동을 생략하지 않는다. 무엇을 다시 묻고 무엇을 진료할 때 말해야 하는지 문장을 끝까지 쓴다.
- 숫자 제목의 답은 `같은 쪽인지가 첫째입니다`, `첫째는 … 것입니다`, `이럴 때 볼 것은 두 가지입니다`, `아픈 곳을 말하는 것이 첫 번째입니다`처럼 계산식으로 쓰지 않는다. 번호 소제목에서 완전한 결론이나 행동을 바로 말하고, 그 결론을 이해하는 데 필요한 설명은 문단 수를 제한하지 않고 충분히 쓴다.
- 마지막 번호 뒤에는 주제에 맞는 마무리 소제목을 둔다. 마무리는 번호를 기계적으로 복창하지 않되, 독자가 꼭 기억해야 할 안전 행동이나 진료 기준은 자연스럽게 다시 짚을 수 있다. 한 문단·두 문장·쉼표 한 개 같은 숫자 제한은 적용하지 않으며, `판단이 회복을 좌우합니다·다시 걷기 위한 출발입니다` 같은 추상 표어 대신 구체 증상과 다음 행동을 말한다.
- 소제목도 `발목이 굽혀지고 골반이 기우는가`, `먹은 음식보다 먹는 방법까지`, `소화제보다 병원 검사가 먼저인 때`처럼 조사·명사 조각으로 끝내지 않는다. 원장의 질문·관찰 또는 환자의 행동이 끝까지 들리는 완전한 생활어 문장으로 쓴다.
- 읽는 시간 안내 장치는 사용자가 읽는 시간을 명시적으로 요청한 경우에만 선택한다. 숫자 제목이라는 이유만으로 `3분만 읽어 보세요`, `4분만 읽어 보세요`를 넣지 않는다.

사용자 확정 변환 기준:

- 실패: `불면증 치료 전에는 잠든 시간만 묻지 않습니다.`
- 통과: `저희 동천동 한의원 금손한의원에서는 불면증 치료 전에 절대 취침시간만 물어보지 않습니다. 환자의 생활패턴을 샅샅이 파악해서 근본적인 원인을 찾고자 합니다.`
- 실패: `잠든 시간만 확인해서는 왜 자꾸 깨는지 알기 어렵습니다.`
- 통과: `평소 취침시간만 파악해서는 왜 밤마다 자꾸 잠에서 깨는지 절대 알 수 없습니다.`

예문의 단어만 다른 질환에 복사하지 않는다. 모든 문단에서 `주체를 밝힘 → 판단을 직접 말함 → 실제 진료 행동을 설명함 → 이유나 목적까지 말함`이라는 작성 방식을 적용한다.

- 실패: `몸 상태를 가볍게 넘기지 말고 통증을 참고 일상을 밀지 마세요.`
- 통과: `사고 직후 통증이 없더라도 그냥 지나치면 안 됩니다. 목이나 허리가 아픈데도 출근·운전·운동을 평소처럼 계속해서도 안 됩니다.`
- 실패: `경과가 달라지면 다시 움직임과 일상을 살핍니다.`
- 통과: `통증이 심해지거나 새로 저리기 시작하면 목과 허리를 다시 진찰하고 필요한 검사가 있는지 확인합니다.`
- 실패: `운동보다 진료 순서가 앞서는 신호입니다.`
- 통과: `다리에 힘이 빠지거나 소변을 보기 어려워졌다면 운동을 멈추고 바로 병원 검사를 받아야 합니다.`
- 실패: `어떤 자세에서 통증이 시작되는지가 더 많은 이야기를 해 줍니다.`

### 진료실 발화 가능성 검사

완성 문장마다 `금손한의원 원장님이 환자 앞에서 실제로 이렇게 말할까?`를 다시 묻는다. 조금이라도 글말처럼 들리면 단어만 바꾸지 말고 짧고 직접적인 생활어 문장으로 다시 쓴다. `-는지와 -는지`, 검사·신체 부위의 의인화, 치료 필요 여부를 되풀이하는 순환문, 답의 개수를 세는 계산형 회수를 별도로 찾는다. 블라인드 낭독에서 고쳤다고 기록한 실패 문장은 저장된 최종 평문에서 다시 검색하며, 그대로 남아 있으면 완료로 보고하지 않는다.

모든 문장은 실제 주어·목적어·서술어와 평이한 뜻을 확인한다. 다만 문장을 미리 정한 여덟 가지 형태로 분류하거나 `clinicUtteranceForm` 라벨을 붙이지 않는다. 자연스러운 원장 설명, 원인 설명, 필요한 전환과 요약까지 문맥에서 실제 역할이 있으면 허용한다.

`제가·사실·그런데·~죠`와 대화형 어미의 집계값은 검수 보조값이지 작성 목표가 아니다. `A라고 단정할 수 없습니다 → 반대로 B라고 볼 수도 없습니다 → 사람마다 다릅니다 → 진찰이 필요합니다` 같은 대칭형 전개, 환자 상태와 연결되지 않은 치료명 나열, `확인합니다·봅니다·정합니다`의 반복은 개별 금지어가 없어도 다시 쓴다.

### writing-voice 최종 재청취 검사

초안 단계의 발화 편집과 별개로, SEO까지 반영된 완성 산문을 마지막에 한 번 더 읽는다. 먼저 제목, 내용 원자와 흐름 비트 순서, 사실과 의료 경계, 선택한 설득 장치, 고정 구성 요소를 동결한다. 그런 다음 제목부터 마무리까지 실제 말하는 속도로 듣고 상투적인 연결 문장, 같은 호흡의 반복, 박준희 원장의 확신·유보·주의가 무난하게 평평해진 곳, 독자 고민보다 블로그다운 요약이 앞선 곳을 찾는다. 이와 별도로 모든 `상태·변화·반응·순서·방향·기준·과정·양상·흐름·신호·움직임·생활·모습·단계`를 검색하고, 주체·실제 행동·이유가 같은 문장에 보이지 않는 추상 포장어를 전부 다시 쓴다.

수정한 문단마다 `더 자연스럽게`가 아니라 `환자가 어느 동작에서 아픈지 바로 떠올리게 함`, `지나친 유보 때문에 흐려진 안전 지시를 직접 들리게 함`처럼 표현이 수행할 일을 내부 기록에 남긴다. 부분 수정 뒤에는 글 전체를 다시 읽는다. `assets/writing-voice-final-review-contract.json`과 `scripts/validate_final_voice_review.py`를 통과하지 못하면 HTML 조립이나 완료 보고로 넘어가지 않는다.

### 동일 공통 원고 A/B 최종 윤문 테스트

사용자가 같은 주제의 최종 윤문기 차이를 테스트한다고 명시하면 레퍼런스와 예약, 제목, 내용 원자, 흐름, 금손 사실, 의료 경계, 생활어 초안, 발화 편집, SEO 완성은 한 번만 수행한다. SEO까지 끝난 같은 `sharedBeforeBody`를 복제한 뒤 마지막 단계만 분기한다.

- A안: 번들 `$writing-voice`와 `writing-voice-final-rehear-v1`
- B안: 설치된 `$humanize-korean`과 `humanize-korean-final-pass-v1`. B안에는 `$writing-voice`, A안 수정문, `writingVoiceReview`, writing-voice article 속성을 넣지 않는다.

B안은 `$humanize-korean`의 `SKILL.md`와 `references/quick-rules.md`를 읽고 장르 `블로그`, 강도 `기본`, 최소심각도 `S1`로 실행한다. quick-rules ID가 있는 표현만 고치고, 변경률 30% 이하·잔존 S1 0건·자체검증 6/6·등급 A 또는 B를 요구한다. `assets/humanize-korean-final-review-contract.json`, `scripts/validate_humanize_final_review.py`, [references/final-humanize-korean-review.md](references/final-humanize-korean-review.md)를 모두 따른다.

두 안은 공통 초안을 의도적으로 공유하므로 `validate_natural_speech_suite.py --expected-count 1`을 각각 실행한다. 비교 단계에서는 평문 두 안과 검수 영수증까지만 만들고, 모바일·이미지·표·HTML·최근 글 이력은 사용자가 선택한 한 안에만 적용한다.

## 입력과 자동 작성

이 스킬에는 사용자가 선택하는 실행 모드가 없다. 항상 자동 작성으로 진행하며 선택 메뉴를 만들지 않는다. 예전 방식의 모드명이 요청에 들어와도 별도 흐름으로 전환하지 않는다.

입력값은 한 응답에 하나씩 다음 순서로 받는다. 이미 받은 값은 다시 묻지 않는다.

1. 글 주제가 없으면 시작 브리핑 두 문장 뒤에 `assets/topic-recommendation-contract.json`과 `assets/beomeo-topic-idea-library.json`의 허용 필드만 읽고 서로 다른 정보형 주제를 `1.`부터 `10.`까지 정확히 10개 보여 준다. 목록 바로 아래에 `1~10번 중 작성할 주제를 선택하거나, 원하는 주제를 직접 입력해 주세요.`만 묻고 기다린다.
2. 사용자가 1~10번을 입력하면 해당 추천 주제를 글자 하나 바꾸지 않고 확정한다. 번호 대신 텍스트를 입력하면 사용자 직접 입력 주제로 취급해 그대로 확정한다. 사용자가 최초 요청에서 글 주제를 직접 제공했다면 10개 추천 단계를 건너뛴다.
3. 글 주제는 있고 메인키워드가 없으면 `메인키워드를 입력해 주세요.`만 묻는다.
4. 글 주제와 메인키워드가 모두 있고 확정 제목이 없으면, 리서치·레퍼런스 탐색·최근 글 이력 확인·편집 마스터 선택을 실행하지 않고 `assets/title-recommendation-contract.json`에 맞는 제목 5개를 바로 번호로 보여 준다. 그 아래에 `1~5번 중 사용할 제목을 선택하거나, 원하는 제목을 직접 입력해 주세요.`만 묻고 기다린다.
5. 사용자가 1~5번을 입력하면 해당 추천 제목을 글자 하나 바꾸지 않고 확정한다. 번호 대신 제목을 입력하면 사용자 직접 입력 제목으로 취급한다. 사용자가 최초 요청에서 확정 제목을 직접 제공했다면 5개 추천 단계를 건너뛴다.
6. 확정 제목까지 받으면 다른 사전 확인 없이 끝까지 자동 작성한다. 이미 받은 주제·메인키워드·제목은 다시 묻지 않는다. 최근 글과의 주제 중복 검사를 이유로 중단하거나 새 주제·새 각도를 요구하지 않는다.

1. 사용자가 입력한 글 주제를 실제 글의 주제로 고정하고, 메인키워드의 띄어쓰기와 표기를 정확히 고정한다.
2. 주제와 메인키워드만으로 `workflowStage=title-first` 제목 후보 5개를 만든다. 이 단계에서는 `referenceMasterId`·`titleMechanismId`를 비워 두고, `validate_title_recommendations.py`의 빠른 형식·금지표현·확인된 11년차 수치 검증만 통과시킨다.
3. 사용자가 고른 추천 제목 또는 직접 입력 제목을 글자 하나 바꾸지 않고 확정한다. 직접 입력 제목은 우선 메인키워드 시작·공백 제외 30자·근거 수치·금지 표현만 검사한다.
4. 확정 제목을 포함해 `scripts/select_general_information.py --topic "{사용자 입력 주제}" --keyword "{사용자 입력 메인키워드}" --title "{확정 제목}" --json`을 처음 실행한다. 저장 레퍼런스 여러 편의 주제·제목 일치 일반 정보 원자를 찾고 의미 중복을 제거한다. `광주 한의원`, `동천동 한의원` 같은 지역·업종 메인키워드는 SEO 앵커일 뿐 정보 검색 주제가 아니므로 선택·검색 점수에서 제외한다.
5. 결과의 `webSearch.required=true`이거나 확정 제목의 답이 부족하면, 결과의 한국어 검색어를 `search_naver_background.py`에 넣고 네이버를 백그라운드 검색한다. `fetch_naver_post_text.py`로 서로 다른 발행자 2곳 이상의 관련 본문을 읽고 일반 정보 원자로 다시 적는다. 치료·검사·안전 내용은 한국 공식 의료 출처를 하나 이상 포함한다. 저장 자료가 없다는 이유로 사용자의 주제를 거절하거나 다른 건강 문제로 바꾸지 않는다.
6. `scripts/select_reference_master.py --type 정보전달형 --topic "{사용자 입력 주제}" --title "{확정 제목}" --json`으로 기존 글 구조를 담당할 편집 마스터 한 편을 고른다. 명시한 불면증은 갱년기 맥락이 아닌 경우 `INFO04`, 트라우마·PTSD는 `INFO11`을 열 수 있으며 민감 주제가 아닌 요청은 이 두 마스터를 fallback으로 쓰지 않는다. 이 한 편의 `referenceWritingIntelligence`와 `flowBeats`만 제목 심리·도입 설득·정보 공개 흐름·전환·마무리에 사용한다.
7. 선택 마스터의 허용 장치 가운데 확정 제목의 실제 문구와 맞는 `titleMechanismId`를 내부적으로 대응하고, `validate_title.py --editorial-close --reference-master-id 선택ID --title-mechanism-id 선택장치`로 확정 제목을 다시 검사한다. 숫자 답을 약속한 경우에만 리서치에서 확보한 실제 답 수로 `--answer-count N`을 추가한다. 답이 부족하면 같은 내용을 쪼개거나 제목을 임의 수정하지 않고 새 제목 선택만 요청한다.
8. [references/reference-editorial-reasoning.md](references/reference-editorial-reasoning.md)에 따라 `독자 상태 → 제목 장치와 이유 → 도입 장치와 이유 → 주제별 보상 → 흐름 비트별 역할과 전환 → 편집 마스터의 업체 사실 슬롯을 금손 사실로 교체하거나 생략 → 마무리 감정` 판단 카드를 내부적으로 만든다. 이어 `mergedInformationAtoms[].id → 출처 ID → 확인된 일반 정보·금손 사실 → 환자가 겪는 장면`을 대응하고, 일반 정보 원자를 `content-sources.json`에 합쳐 출처별 차단 엔터티와 제목 답 개수를 기록한다.
9. `sourceProseWithheld=true`, `contentAtomCoverageRequired=true`, `sourceSentenceImitationBlocked=true`, `referenceEditorialReasoningEnabled=true`, `goldhandFactReplacementRequired=true`, `voiceProtocolId=natural-speech-rewrite-protocol-v1`, `voiceProfileId=goldhand-official-voice-v1`, `finalVoiceReviewRequired=true`와 `validate_general_information_library.py`, `validate_information_sources.py` 통과를 확인한 뒤에만 초안을 쓴다. 초안 직전에 [references/direct-clinic-voice-generation-prompt.md](references/direct-clinic-voice-generation-prompt.md)와 [references/v113-approved-writing-style.md](references/v113-approved-writing-style.md)를 새로 읽고 최상위 표현 지침으로 적용한다. `mergedInformationAtoms`를 사실 골격으로, 단일 편집 마스터의 `flowBeats`를 기존 편집 순서로 사용해 SEO·HTML·이미지·모바일 줄바꿈이 없는 평문을 먼저 쓴다. 번호 답마다 문단·문장 수를 미리 배정하지 않고, 결론에서 환자 장면·원인·문진·안전 기준·치료 판단으로 자연스럽게 이어지는 v1.13 호흡으로 충분히 설명한다. `묻다·듣다·보다·설명하다·권하다·치료하다`마다 실제 주체와 구체 목적어를 붙이고, 나열 수·목적어 호응·생략된 행동·기본 동사를 따로 확인한다. 별도 발화 편집 뒤 기본 원고는 `writing-voice-final-rehear-v1`로 최종 재청취하되 고칠 곳이 없으면 원문을 유지한다.
10. callilife에서 주제에 맞는 작품 3~4개를 고르고 작품 상세 미리보기를 생성 레퍼런스로 확보한다. 각 작품이 인물 중심인지 비인물 중심인지 먼저 분류한다. 인물 중심이면 표현·그림체를 유지하고 인물만 미세하게 바꾸며, 비인물 중심이면 내용·배치를 유지하고 그림체만 미세하게 바꾼다. 생성본만 로컬에 저장하고, 원장 소개표 뒤 첫 두 개 설명 섹션에서 각 생성본이 설명하는 핵심 단어가 실제로 들어간 모바일 문단 바로 뒤에 한 장씩 삽입한다. 최소 1장은 첫 번째 설명 섹션에 둔다. 세 번째 설명 섹션 이후나 글 끝에 모아 두지 않는다. 구매·가격·라이선스 선택은 묻지 않는다.
11. 진료 사진 배치를 `before-credential` 1장 또는 `closing-trust` 2장 중 하나로 정한다. `before-credential`은 `recommend_media.py`가 주제의 실제 장면과 맞고 바로 직전 완료 글에 쓰지 않은 사진만 고른다. `closing-trust`는 질환·부위·본문 문맥을 비교하지 않고 시각 검수된 원장-환자 치료·진찰·상담·검사 사진 2장을 고른다. 직전 글 미사용 사진을 먼저 쓰고 부족하면 직전 글 승인 사진도 재사용한다. 모든 후보는 `bundledPath`·SHA256·공식 원본 URL·`approvedAlt`가 일치해야 한다.
12. 진료 사진과 별도로 `recommend_closing_trust_media.py --json`을 실행해 검수된 협약·수료증·기부·봉사 사진 1장을 고른다. 진료 사진은 `data-real-photo="true"`와 `data-real-photo-slot="before-credential|closing-trust"`, 마무리 신뢰 사진은 `data-trust-photo="true"`와 `data-trust-photo-slot="closing-credential-trust"`로 완전히 분리한다. 신뢰 사진은 별도 소개·맥락·캡션 문장 없이 `data-image-placement="closing-credential-trust"`로 두고 진료시간 안내 전 마지막 이미지로 삼는다. 이 별도 신뢰 사진은 바로 직전 완료 글과 겹치지 않게 회전한다.
13. `validate_general_information_library.py`, `validate_information_sources.py --input content-sources.json --article article.html`, `validate_reference_learning.py`, 선택 윤문기에 맞는 `validate_final_voice_review.py` 또는 `validate_humanize_final_review.py`, `validate_natural_speech_suite.py`, `validate_reference_reconstruction.py --editorial-close`, `validate_copy_overlap.py`, `validate_goldhand_voice.py`, `validate_article.py --editorial-close`를 모두 통과한 원고만 완성한다. writing-voice article은 기존 두 속성을, humanize-korean article은 `data-final-prose-reviewer="humanize-korean"`, `data-final-prose-review="humanize-korean-final-pass-v1"`, `data-final-prose-status="pass"`를 사용한다. 최근 3개 이력에는 사용자가 선택한 한 원고만 기록하되, 이 기록을 이후 글의 주제 중복 차단에 사용하지 않는다.
14. `build_naver_copy_page.py`가 글을 `clinic-info` 운영정보 표에서 끝내고, 운영정보 뒤의 `<함께 보면 좋은 글>`·최신 네이버 블로그 링크·네이버 지도를 만들지 않는지 확인한다. 복사 미리보기는 `relatedLinks=0`, `maps=0`, `nativeModules=0`, `inputBuffer=true`, `requiresNativeFinisher=false`여야 하며 다른 본문 출력은 이전 계약과 같아야 한다.
15. 제목의 실제 답을 만들 필수 사실이 없거나, `before-credential` 문맥 사진·전체 승인 진료 사진 풀·별도 마무리 신뢰 사진 풀의 절대 수량이 부족할 때만 필요한 결정을 짧게 묻는다. `closing-trust`는 주제와 안 맞거나 직전 글에 썼다는 이유로 멈추지 않는다. 두 풀은 서로 대체하지 않는다.

자동 작성한 완성 글은 지역명·상호·운영정보를 가려도 독자가 가져갈 수 있는 원인 설명, 자가 점검, 생활관리, 치료·검사 판단이 남아야 한다. `한의원 고르는 법`, `추천하는 이유`, `선택 기준`, `잘하는 곳의 조건`처럼 업체 선택을 본문 주제로 삼지 않는다. 포괄 키워드를 받았다는 이유로 업체소개형이나 병원 비교형으로 전환하지 않는다.

자동 작성의 정보 주제는 증상형에만 고정하지 않는다. 사용자가 치료 적용·중단·시기·주의를 주제로 입력하면, 금손에서 실제 사용하는 치료 또는 독자가 이미 사용 중이라고 가정할 수 없는 일반 의료 주제를 중심으로 `무엇을 위한 치료인가 → 어떤 상태를 먼저 구분하는가 → 언제 고려하는가 → 치료만으로 부족할 수 있는 조건 → 다른 검사·치료가 먼저인 경계`를 설명한다. 추나요법의 적용 기준·치료 뒤 관리뿐 아니라 위고비·마운자로 사용 중단 뒤 체중관리처럼 독자 판단에 실제 도움이 되는 주제도 포함할 수 있다. 다만 금손한의원이 해당 약을 처방하거나 특정 장비·프로그램을 제공한다고 쓰지 않는다.

## 제목 계약

- 추천 제목은 정확히 5개이며 모두 서로 달라야 한다. 추천 목록 아래에는 `1~5번 중 사용할 제목을 선택하거나, 원하는 제목을 직접 입력해 주세요.`를 표시한다.
- 정확 메인키워드는 제목의 첫 글자부터 시작하고 제목 전체에 정확히 한 번만 쓴다.
- 제목은 공백 제외 30자 이내다.
- 추천 제목마다 `최악의·절대·반드시·치명적인·위험한·망치는·놓치면 손해·후회하는·경고하는·피해야 할`처럼 독자가 바로 이해하는 강한 표현을 하나 이상 쓴다. `나쁜·안 좋은·좋지 않은` 같은 약한 표현은 추천 후보로 통과시키지 않는다.
- 강한 표현은 독자가 피해야 할 습관·행동·신호·실수 또는 알아야 할 핵심 정보에 붙인다. 치료 결과 보장, 질환 공포 과장, 타 기관 비방에는 붙이지 않는다.
- 각 추천 제목은 확인된 금손 경력 `11년차` 또는 `1가지·2가지·3가지` 답 개수 중 하나 이상을 쓴다. 다섯 개 중 `11년차` 제목은 최소 1개, 1~3가지 제목은 최소 3개다.
- 각 추천 제목은 `readerStake=benefit|loss-prevention`을 내부 기록하고, 독자가 얻을 이득 또는 피할 손해가 제목 표면에서 바로 보여야 한다.
- 제목은 본문이 실제로 답할 구체적인 원인·기준·주의점·시기·원칙을 약속하면서 선택 프로필의 제목 장치가 독자에게 작용한 이유를 유지한다.
- 답 개수, 확인된 권위, 대비, 지식 공백, 생활 장면, 결과의 모순 가운데 `titleMechanism.allowedIds`가 허용한 장치를 선택한다.
- 레퍼런스의 `29,000명`, 경력, 원장 수 같은 권위 수치는 가져오지 않는다. 같은 신뢰 기능에 맞는 금손 사실이 `clinic-facts.md`에 있고 주제와 관련될 때만 교체한다. 없으면 생략하고 진찰·설명 방식이나 독자의 구체적인 궁금증으로 신뢰를 만든다.
- `11년차`는 원장 경력에만 연결한다. 누적환자, 누적추나, 만족도, 재방문율, 지역 1위는 쓰지 않는다.
- `1가지·2가지·3가지`를 쓴 제목은 사용자가 선택한 뒤 같은 개수의 실제 답을 본문 구조로 고정한다. 답 개수를 맞추려고 같은 내용을 쪼개지 않는다.
- 사용자가 직접 입력한 제목은 문구를 임의로 바꾸지 않는다. 메인키워드 시작·공백 제외 30자·근거 수치·숫자 답 개수·금지 표현 검증에 실패하면 한 번에 문제 하나만 알리고 새 제목을 받는다.
- 레퍼런스 제목의 흔한 검색 표현과 질문형·이유형 문법뿐 아니라 권위, 대비, 궁금증, 구체적 약속이 왜 작동하는지 해석해 옮길 수 있다. 경력·수치·업체명·지역·치료 성과·고유 프로그램은 확인된 금손 사실 없이 바꾸어 옮기지 않는다.
- `살이 안 빠진다`처럼 사람이 흔히 쓰는 말을 표절 회피 목적으로 `체중이 그대로라면 먼저 볼 기록` 같은 추상어로 치환하지 않는다.
- 후보마다 독자가 얻을 판단을 한 문장으로 답할 수 없으면 폐기한다.
- 포괄적인 지역·업종 키워드가 들어와도 제목의 실제 약속은 구체적인 증상·원인·생활 조건 또는 특정 치료의 원리·적용 기준·효과가 더딘 조건·주의점이어야 한다. 한의원 자체를 고르는 법이나 추천 이유를 제목의 답으로 삼지 않는다.
- 추천 5개는 `scripts/validate_title_recommendations.py`, 확정 제목은 `scripts/validate_title.py`를 통과시킨다.

## 작성 순서

아래 단계의 작업 흐름은 유지하되 내용은 모두 금손 계약으로 수행한다.

7단계에서는 [references/v113-approved-writing-style.md](references/v113-approved-writing-style.md)의 문단 호흡을 먼저 적용한다. 13단계 전 문장 의미 감사에서는 형식 라벨을 붙이지 않고 실제 주어·목적어·서술어·평이한 뜻과 문맥 속 역할만 확인한다.

- **주제 10개 추천·선택 사전 단계**: 글 주제가 없을 때 허용된 정보형 아이디어 10개를 번호로 보여 준다. 최근 글 이력은 읽지 않으며, 사용자는 1~10번을 고르거나 원하는 주제를 직접 입력한다.
1. **빠른 제목 5개 추천·선택**: 주제와 메인키워드만으로 제목 계약을 지킨 후보 5개를 먼저 보여 준다. 리서치·레퍼런스·최근 이력·편집 마스터는 읽지 않는다.
2. **다중 일반 정보 수집**: 확정 제목 뒤 저장된 관련 레퍼런스 여러 편의 일반 정보 원자를 모아 의미 중복을 제거하고, 부족하면 한국어 네이버 백그라운드 검색으로 보충한다. 출처 업체 정보와 원문 문장은 전부 차단한다.
3. **단일 편집 마스터·판단 카드 고정**: 확정 제목과 주제로 기존 글 구조용 `referenceWritingIntelligence` 한 편을 고르고 독자 상태, 제목 장치와 심리, 도입 장치와 보상, 흐름 비트와 전환, 미세 표현 기능, 신뢰 사실 슬롯, 마무리 감정을 적는다. 콘텐츠 출처가 여러 편이어도 편집 마스터와 기존 구조는 하나다.
4. **내용 원자표·사실 팩·제목 재검증**: 저장·웹 일반 정보 원자를 `mergedInformationAtoms`로 합치고 금손 사실·의학 설명·예외·자가관리·금지 주장을 분리한다. 선택 마스터의 제목 장치와 숫자 약속의 실제 답 개수까지 확정 제목을 재검증한다.
5. **도입 작성**: 선택 글의 독자 고민을 금손 맥락으로 바꾼 질문 2~3개를 첫 보이는 문장으로 연속 배치하고, 그 뒤에 고정 인사를 정확히 한 번 둔다. 이어 선택 프로필의 도입 설득 장치와 주제별 보상을 배치한다. 두 질문을 `증상명 때문에 …나요?` 같은 틀로 나란히 쓰지 않고, 각 질문이 서로 다른 생활 장면과 다른 호흡을 갖게 한다. 분 단위 숫자 장치를 선택했을 때만 실제 분량에 맞는 1~5분을 쓴다. 공감 또는 핵심 문구 한 곳을 노란색으로 강조한다.
6. **1:1 흐름 대응표 작성**: 각 `flowBeats[].id`와 `mergedInformationAtoms[].id`에 일반 정보, 금손 사실, 환자가 겪는 장면, 다음 문단이 필요한 이유를 대응한다. 숫자 약속 제목은 동일 개수의 실제 번호 답에 별도로 대응한다.
7. **v1.13 사용자 승인 방식으로 생활어 평문 초안 작성**: 초안을 쓰기 전에 [references/direct-clinic-voice-generation-prompt.md](references/direct-clinic-voice-generation-prompt.md), [references/v113-approved-writing-style.md](references/v113-approved-writing-style.md), `natural-speech-rewrite-protocol.md`를 끝까지 읽는다. 편집 마스터·미세 표현·일반 블로그 문체보다 v1.13 승인 호흡을 우선해 SEO·HTML·이미지·강조·모바일 줄바꿈 없는 평문을 쓴다. 먼저 결론을 분명히 말하고 환자의 실제 장면, 원인, 금손이 묻거나 진찰하는 내용, 안전 기준과 치료 판단을 문맥에 맞게 이어 간다. 번호 답마다 필요한 내용을 여러 문단으로 충분히 설명하며 문장 수·쉼표 수·문단 수·행동 종류를 미리 할당하지 않는다. 보통 두세 문장이 한 문단으로 읽히는 호흡을 참고하되 숫자에 맞추려고 자연스러운 문장을 삭제하거나 압축하지 않는다. 독자에게 직접 동작을 요청하는 표현과 `저는 환자에게 … 해 보게 합니다` 같은 진료 설명을 모두 허용하되 누가 움직이고 누가 묻거나 보는지 분명하게 쓴다. 같은 핵심 질문이나 안전 행동도 설명상 필요하면 도입·본문·마무리에서 자연스럽게 되짚는다. 정확 키워드는 `저희 {정확 메인키워드} 금손한의원에서는` 구조를 한 문장 안에 완전하게 넣는다. 나열 수와 수사·지시어, 목적어와 서술어, 생략된 마시기·먹기·맡기 행동, 기본 동사와 오탈자를 문장마다 확인한다. `잠 밖에 있습니다·몸의 흐름을 봅니다·회복의 방향을 찾습니다`처럼 구체적인 뜻이 없는 AI 표현은 쓰지 않는다.
8. **독립 발화 편집**: 새 패스에는 편집 판단 카드·내용 원자표·금손 사실 팩·평문 초안을 전달한다. 문장마다 `박준희 원장이 환자를 앞에 두고 실제로 이렇게 말할까?`, `누가 무엇을 하고 왜 그렇게 하는지가 한 번에 보이는가?`, `환자가 듣자마자 어느 시간·동작에서 어디가 어떻게 불편한지 떠올릴 수 있을까?`, `주어·목적어와 서술어가 일상 한국어에서 실제로 함께 쓰이는가?`, `앞에서 나열한 항목 수와 뒤의 수사·지시어가 맞는가?`, `앞 문장과 다른 새 정보를 주는가?`, `레퍼런스에서 배운 설득 기능이 금손식 표현 안에 남아 있는가?`를 묻는다. 번역투·작문체·감성 문장·추상 압축 표현·대칭형 안전 문장·치료명 나열은 단어만 바꾸지 말고 `주체 → 실제 행동 → 이유·목적`이 보이도록 문장 구조부터 다시 쓴다. 특히 `어떻게 달랐는지·이 차이를 함께 봅니다·증상에 따라 달라집니다·필요한 범위·붓기가 커지다·두통이 덜 오다·먹고 언제 더부룩한지·시각과 거리를 듣다`처럼 구체적인 앞 문장에 기대거나 뜻만 짐작되는 문장도 전부 다시 쓴다. 환자의 감각을 원장이 `본다`고 했는지, 원장이 먼저 묻는 내용을 막연히 `듣는다`고 했는지, 실제 치료 동작을 `어느 부위에 왜 치료`로 감췄는지, 가까운 자리에서 같은 조사·부사를 반복했는지 반대로 의심해 다시 읽는다.
9. **독립 검수**: 제목, `content-sources.json`, 편집 판단 카드, 사실 팩, 원자·흐름 비트별 본문 대응, 금손 말투 프로필, 발화 편집이 끝난 평문을 새 패스에서 읽는다. 모든 출처 업체 엔터티와 7어절 이상 원문 복사를 막되, 제목 심리·도입 보상·전환·마무리 감정이 사라졌다면 다시 쓴다. `manualReview.directVoiceSentenceAudit`에는 `상태·변화·반응·방향·기준·순서·과정·양상·흐름·신호·움직임·생활·모습·단계·차이·범위`가 남은 최종 문장을 빠짐없이 그대로 적고, 시간·동작·증상·진료 행동이 실제로 보일 때만 `kept-concrete`로 유지한다. `revisionHistory`는 요약이 아니라 실제 `수정 전 → 수정 후` 문장으로 기록한다.
10. **v1.13 호흡 사전 검수와 부분 수정**: [references/v113-approved-writing-style.md](references/v113-approved-writing-style.md)의 승인 원고처럼 결론과 이유, 생활 장면과 진료 설명이 자연스럽게 이어지는지 읽는다. 번호 답이 지나치게 짧아 핵심 이유가 빠졌거나, 반대로 질문과 명령만 줄줄이 이어져 설명이 끊긴 곳을 고친다. 문장·쉼표·문단 개수 자체로 실패시키지 않는다. 같은 질문이나 진찰이 다시 나와도 독자의 이해와 안전 기준을 되짚는 역할이 있으면 유지하고, 분량을 채우기 위한 동일 문장 복사만 걷어낸다. 주어·목적어·서술어 호응, 수 일치, 생략된 행동, 오탈자, 추상적인 AI 표현을 우선 검사하며 문제가 없는 문단은 고정한다.
11. **SEO 산문 완성**: 자연스러운 글의 새 정보를 늘리지 않고 정확 키워드를 일반 본문에 1~2회 넣는다. `광주 ○○ 한의원 진료를 받으러 오셨다면`, `광주 ○○ 한의원 진료에서도`, `광주 ○○ 한의원에 오실 때는`, `저희 금손한의원은 광주 ○○ 한의원 진료에서`처럼 검색 문장을 만들지 않는다. 사용자 승인 방식인 `저희 {정확 메인키워드} 금손한의원에서는 {구체 질문·진찰}` 구조를 글자 그대로 한 문장에 사용하고 바로 다음 문장에 그 이유를 직접 쓴다. 입력 키워드로 만든 이 승인 문자열이 최종 평문에 실제로 존재하는지 검사하며, 키워드 문장과 병원명 문장을 분리하면 실패다. 제목 약속, 공백 제외 분량, 각 원자 근거 구절이 모두 남았는지 확인한다.
12. **최종 윤문**: 기본 원고는 내부 JSON의 `writingVoiceReview`에 writing-voice 최종 재청취 기록을 남기고 기존 계약을 통과시킨다. 명시적 A/B 비교에서는 동일한 검수 직전 `beforeBody`를 A안과 B안에 넣는다. A안은 `writingVoiceReview`, B안은 `humanizeKoreanReview`만 기록한다. B안의 변경 문단에는 quick-rules ID, 계산 변경률, 등급, 자체검증 6항과 동결값을 남긴다. 두 안은 각자 `validate_natural_speech_suite.py --pre-blind --expected-count 1` 1차 검사를 통과시키며, 의도적으로 같은 공통 초안을 공유한 두 안 사이에는 교차 원고 복제 검사를 적용하지 않는다.
13. **기계 통과 뒤 블라인드 전체 낭독·전 문장 의미 감사**: 새 패스에는 제목과 최종 평문만 전달하고 말투 금지 패턴·검색 목록·검사 결과·SEO 수치·레퍼런스 문장을 숨긴다. `박준희 원장이 환자 한 명에게 실제로 말할까`, `한 번 듣고 바로 알까`, `결론에서 생활 장면과 이유가 자연스럽게 이어지는가`, `질문과 명령만 이어지는 체크리스트가 아닌가`, `v1.13 승인 원고처럼 필요한 설명을 충분히 했는가`를 묻고 전체를 읽는다. 이어 모든 문장을 등장 순서대로 보며 실제 주어·목적어·서술어·평이한 뜻, 조사·병렬 구조, 수 일치, 의도와 문자 그대로의 뜻을 확인한다. `clinicUtteranceForm`은 기록하지 않는다. 어색한 문장이 있으면 고치고 전체를 다시 읽으며, 고칠 곳이 없으면 억지로 바꾸지 않고 `no-change-needed`로 기록한다. `sentenceMeaningAudit`의 전 문장 대응과 두 번째 전체 낭독 잔존 0건을 기록한 뒤 `validate_natural_speech_suite.py --expected-count 1`을 다시 통과시킨다.
14. **모바일·이미지·순정 컴포넌트·HTML 조립**: 블라인드 재낭독과 최종 기계 재검사가 끝난 문장의 표현을 바꾸지 않은 채 모바일 시각 줄로 나눈다. GPT Image 생성본 3~4장은 원장 소개표 뒤 첫 두 개 설명 섹션에 관련 문단별로 배치하고 최소 1장은 첫 섹션에 둔다. 승인 원장-환자 실제 사진은 원장 소개표 바로 위 1장 또는 글마무리 신뢰 구간 2장 중 한 방식만 쓴다. 원장 소개표 위 1장은 바로 앞 문단·anchor·승인 장면을 맞춘다. 글마무리 2장은 본문과 장면이 달라도 되며 `closing-clinical-gallery`로 이어 붙이고, 직전 글 미사용 사진을 우선한 뒤 부족하면 승인 사진을 재사용한다. 모든 글을 중앙 정렬하고 필요한 순정 컴포넌트를 배치한다.
15. **발행 게이트·이력 기록**: 선택된 최종 윤문기의 pass 상태, 블라인드 전체 낭독 2회와 잔존 0건, 기존 구조, 제목 숫자 약속, 일반 정보 원자 출처, 출처 업체 누출 0건, 금손 사실 출처, 금손 말투, 진료실 발화 가능성, 원문 문장 중복, 의료 안전, 실제 진료 사진 1장 또는 2장·별도 마무리 신뢰 사진 1장·GPT Image 3~4장을 검사한 뒤 제목·키워드·주제·편집 마스터·윤문기·두 종류 사진의 ID·해시를 최근 3개 이력에 한 번 기록한다. 이 이력은 공식 사진 순환과 작업 기록용이며 다음 글의 사용자 지정 주제를 막지 않는다.

## 본문과 SEO 계약

- 제목과 실제 본문을 합쳐 공백 제외 1,400~1,800자다.
- 정확 메인키워드는 제목 1회, 일반 본문 1회 또는 2회다.
- 표, 이미지 `alt`, 고정 운영정보, 연락처, CTA는 키워드 횟수에서 제외한다.
- 한 문단에는 정확 키워드를 한 번만 쓰며 도입·중반·후반 가운데 자연스러운 1~2곳에 둔다.
- 키워드 수를 맞추려고 의미 없는 문장이나 요약 블록을 덧붙이지 않는다.
- 일반 본문은 `data-mobile-group="true"` 한 묶음에 시각 줄 2개 또는 3개를 두고 `<br>`로 나눈다.
- 한 시각 줄은 공백 제외 10~20자를 목표로 하고 4~24자를 벗어나지 않는다. 글자 수보다 조사·체언·서술어가 어색하게 끊기지 않는 것이 우선이다.
- 모든 일반 본문 묶음 뒤에 `data-preview-gap="true"` 빈 줄을 한 개 둔다.
- 모든 일반 본문과 고정 인사도 `text-align:center`로 출력한다.
- 노란 하이라이트는 `<span data-goldhand-emphasis="highlight" style="background-color:#FFF2A8;">짧은 핵심 결론</span>`, 밑줄은 `<u data-reference-underline-role="key-point">짧은 행동 기준</u>`, 빨간 글씨는 `<span data-goldhand-emphasis="red" style="color:#E53935;font-weight:700;">짧은 안전 경계</span>`만 사용한다.
- 노란 하이라이트는 3개를 사용한다. 1개는 도입의 공감·핵심 문구, 2개는 서로 떨어진 본문 핵심 문구에 둔다.
- 분 단위 읽기 안내는 의료 성과 수치는 아니지만 고정 구조도 아니다. 사용할 때는 1~5분의 구체적인 읽기 비용과 그 글에서만 얻는 보상을 같은 도입 안에 두고, 레퍼런스 완성 문장을 복사하지 않는다.
- 빨간 글씨는 중단·검사·주의 같은 안전 경계에만 쓰고 치료 효과, 가치입증, 예약 유도에는 쓰지 않는다.
- 같은 증상도 원인이 다를 수 있음을 설명하고, 필요하면 다른 검사·기관을 먼저 권하는 경계를 함께 쓴다.
- 시술명을 나열하기 전에 왜 반복되는지, 무엇을 구분하는지, 집에서 무엇을 살필지 설명한다.
- 독자에게 무언가를 시킬 때는 실제 치료·안전·진료에 필요한 행동만 말한다. `스스로 운동을 이어가지 마세요`처럼 번역한 듯 완곡하게 말하지 않고 `혼자 판단해서 운동을 계속하시면 안 됩니다`처럼 바로 알아듣게 쓴다.
- `다시 아파지는 순간을 적어보세요. 그게 다음 실마리가 됩니다`처럼 기록을 권한 뒤 추상적 보상을 붙이지 않는다. 정보가 필요하면 `언제, 어떤 동작에서 다시 아픈지 진료할 때 말씀해 주세요`처럼 왜 필요한지 드러나는 실제 말로 바꾼다.
- 문단마다 독자에게 `적어 보세요·떠올려 보세요·살펴보세요`라고 숙제를 주지 않는다. 꼭 기록이 필요한 주제라도 기록 방법과 사용 목적이 구체적일 때만 한 번 설명한다.
- 추상적인 상태명보다 환자가 실제로 하는 동작과 느끼는 불편을 쓴다. `아픈 자리`는 `아픈 곳`, `걷기가 달라지다`는 `평소보다 걷기 힘들다`처럼 바꾸되, 예시만 치환하지 않고 모든 문장을 같은 생활어 기준으로 다시 읽는다.
- `반응·부담·조건·방향·양상` 같은 명사를 썼다면 바로 뒤에 언제, 어떤 동작에서, 어디가 어떻게 아픈지가 보이는지 검사한다. 보이지 않으면 그 문장을 생활 장면으로 다시 쓴다.
- 합성 환자 사례, 허위 직접 인용, 근거 없는 수치, 결과 보장을 만들지 않는다.
- 강한 예약 유도 대신 필요한 경우 현재 상태를 의료진과 상의해도 좋다는 정도로 끝낸다.

## 이미지와 HTML 계약

- 설명 이미지 3~4장은 시스템 `$imagegen`의 기본 내장 `image_gen` 모드로만 만든다. `scripts/image_gen.py`, CLI/API fallback, `OPENAI_API_KEY` 환경변수 요청은 금지한다. 내장 도구를 현재 작업에서 호출할 수 없으면 API 경로로 바꾸지 말고 앱 업데이트·새 작업의 `$imagegen` 단독 테스트가 필요하다고 정확히 알린 뒤 HTML 조립 전에 중단한다.
- 의료 개념·동작 설명 이미지는 사용자 소유 callilife OGQ 작품을 레퍼런스로 우선한다. `assets/callilife-ogq-media-library.json`에서 주제와 직접 연결된 작품 3~4개를 고르고 `safeAuto=true`와 `ownershipBasis=user-confirmed-2026-08-21`을 확인한다.
- 작품 미리보기는 GPT Image 입력에만 사용한다. 최종 원고에는 `data-media-provider="gpt-image"`, 생성본 `data-local-image`, callilife 작품 상세 URL, `data-generation-owner-authorization="user-confirmed"`, `data-generation-content-preservation="medical-information-layout"`, 그리고 `data-generation-variation-mode="person-identity-subtle-variation"` 또는 `nonperson-style-subtle-variation`을 가진 이미지 3~4개만 넣는다.
- 각 GPT Image `<figure>`에는 `data-image-zone="early-explanatory-body"`, `data-image-placement="after-related-paragraph"`, `data-image-anchor="핵심어1|핵심어2"`를 둔다. 직전의 `data-mobile-group="true"` 문단에는 anchor 가운데 하나가 실제로 있어야 한다. 3~4장 모두 원장 소개표 뒤 첫 두 개 설명 섹션 안에 두고 최소 1장은 첫 섹션에 둔다. 생성본은 이 figure로 최종 article에 들어가야 하며, 별도 파일 링크만 전달하면 실패다.
- HTML 조립 전에 `~/.codex/state/goldhand-clinic-blog/image-host.json`이 없거나 연결 프로젝트가 없으면 확인 질문으로 멈추지 말고 현재 운영체제의 Python으로 `scripts/setup_image_host.py`를 실행한다. 로그인되지 않은 경우에는 로컬 이미지 생성·검수를 먼저 끝낸 뒤 설정을 시작하고, 브라우저가 열리는 즉시 "코드는 입력하지 말고 로그인 후 Allow만 누르세요"라고 한 번 안내한 다음 같은 실행에서 승인 완료를 기다린다. 코드가 비어 있는 인증 화면을 사용자에게 해결하게 하거나 터미널·이메일·계정 설정에서 코드를 찾으라고 하지 않는다. 스크립트가 코드가 포함된 Vercel 완성 주소만 열고 만료 시 새 요청을 한 번 자동 발급한다. 프로젝트 이름·폴더·공개 주소·JSON 입력을 사용자에게 요구하지 않는다. 사용자가 로그인을 취소하거나 외부 연결이 실패했을 때만 생성된 로컬 이미지를 보존하고 자동 이미지 연결이 끝나지 않았다고 정확히 알린다.
- `build_naver_copy_page.py`는 설정된 금손 전용 호스트를 읽어 로컬 생성본을 콘텐츠 해시 파일명으로 게시한다. 게시된 각 URL이 HTTP 200·이미지 MIME인지 확인한 뒤에만 HTML을 저장하며, 게시 실패 시 base64로 우회하지 않고 빌드를 중단한다.
- 복사 버튼은 모든 본문 이미지가 실제로 로드되어 가로·세로 크기를 확인한 뒤에만 활성화한다. 복사 HTML의 각 사진은 네이버 순정 `se-image` 안에 `a[data-linktype="img"][data-linkdata]`와 중첩된 `img.se-image-resource`를 갖고, `data-linkdata`에는 고유 ID·HTTPS 원본 주소·원본 가로·세로가 들어가야 한다. `file:` 경로와 `ClipboardItem` 경로 모두 같은 순정 이미지 구조를 복사한다. 사진 수와 `imageDataLinks` 수가 다르거나 `orphanImageCaptions`가 0이 아니면 발행하지 않는다.
- GPT Image와 별도로 실제 진료 사진은 `before-credential` 1장 또는 `closing-trust` 2장 중 한 구성을 사용한다. `scripts/recommend_media.py`가 `safeAuto: true`인 진료 장면만 고른다. 여기에 `scripts/recommend_closing_trust_media.py`가 `closingTrustEligible: true`인 협약·수료증·기부·봉사 사진 1장을 별도로 골라 진료시간 전 마지막 이미지로 둔다. 두 풀은 수량과 이력을 서로 대체하지 않는다.
- 실제 사진은 `personInteraction: true`, `directorVisible: true`, `sceneType: director-patient-*`로 검수된 원장-환자 치료·진찰·상담·검사 장면만 사용한다. 로고·건물·약·장비·제품·빈 원내 공간은 절대 사용하지 않는다.
- 실제 사진과 GPT 이미지 모두 이미지 앞뒤에 사진을 소개하거나 설명하는 별도 문장, 출처, `AI 생성 이미지`, 장면 이름을 쓰지 않는다. 특히 마무리 신뢰 사진 앞의 협약·수료·기부·봉사 설명 문단도 출력하지 않는다. `<figcaption>`이나 `credential-trust-context`가 하나라도 있으면 발행하지 않는다. 장면 의미와 출처는 `alt`와 검수용 `data-*`로만 관리한다.
- 네이버 순정 이미지 컴포넌트에도 `사진 설명을 입력하세요.`나 빈 `se-caption` 자리표시자를 만들지 않는다. 이미지 본체가 빠졌을 때 캡션만 남는 상태를 정상 복사로 보지 않는다.
- `before-credential`은 바로 직전 완료 글의 ID·파일 해시와 겹치지 않는 문맥 일치 사진 1장을 쓴다. `closing-trust`는 직전 글 미사용 사진을 먼저 쓰되 두 장이 안 되면 직전 글의 승인 사진을 재사용한다. 주제와 장면이 달라도 사진을 빼지 않는다.
- `before-credential` 사진 바로 앞 모바일 문단에는 승인 `placementTerms` 중 하나가 그대로 있어야 하고 figure의 `data-image-anchor`에도 같은 말을 둔다. `closing-trust` 두 장은 관련 문단·anchor를 요구하지 않고 `data-image-placement="closing-clinical-gallery"`를 쓴다. 두 배치 모두 `alt`는 자산의 `approvedAlt`와 정확히 같아야 한다.
- 식별 가능한 환자·가족 얼굴, 이름, 차트, 연락처가 보이는 공식 이미지는 자동 사용하지 않는다.
- 일반 정보 출처와 편집 마스터의 사진 URL은 복사하지 않는다. 필요한 시각 자료는 callilife 본인 작품 목록에서 별도로 찾고 GPT Image로 재생성한다.
- `<article>` 안에는 제목 `h1`, 영문 브랜드 띠, 고정 원장 카드가 없어야 한다.

- 독자 고민 2~3개는 각각 `<blockquote data-reference-role="reader-question" data-question-source="representative-reader-concern" data-naver-native-component="quotation" style="text-align:center;">`로 만든다. blockquote에는 중앙 정렬 외의 배경·테두리·padding 스타일을 넣지 않는다.

## 발행 차단 조건

- 독자 고민 인용이 확정 주제·제목과 연결되지 않거나 2~3개 범위를 벗어남
- 인용 고민들이 제목과 연결되지 않거나 같은 뜻을 반복함
- 해결 방향 예고가 없거나 첫 정보 본문 뒤에 나옴
- 주제가 없는데 추천 주제를 정확히 10개 번호로 보여 주지 않거나, `1~10번` 선택과 사용자 직접 주제 입력을 함께 허용하지 않음
- 사용자가 지정한 주제를 최근 글과 같거나 비슷하다는 이유로 거절·변경·보류하거나 다른 주제·본문 각도로 대체함
- 관련 저장·웹 일반 정보를 한 편만 강제하거나 의미 중복을 그대로 반복함. 저장 정보가 없다는 이유로 주제를 거절하거나 다른 질환 자료를 섞음
- 편집 마스터를 둘 이상 섞거나 콘텐츠 출처의 구조를 가져와 기존 금손 글 구조를 바꿈
- `content-sources.json`, `sourceProseWithheld=true`, `contentAtomCoverageRequired=true`, `referenceEditorialReasoningEnabled=true`, `goldhandFactReplacementRequired=true` 중 하나가 없거나, 선택된 단일 `referenceWritingIntelligence`를 읽지 않고 초안을 시작함
- `mergedInformationAtoms`를 빼거나 완성 본문에 대응되지 않은 원자가 남음
- 어느 출처든 완성 문장·고유 비유·사례를 복사하거나 7어절 이상 연속 일치함. 반대로 편집 마스터의 질문 기능·구체성·리듬·설득 심리를 전혀 해석하지 않고 금손 공통 템플릿만 덮어쓴 경우도 실패
- `goldhand-official-voice-v1` 누락, 1인칭·대화형 종결·솔직한 연결·생활 장면 부족

- `writing-voice-final-rehear-v1` 누락, 완성 산문·SEO 뒤 전체 재청취 미실행, `data-writing-voice-status=pass` 누락, 수정 전후 문단·표현의 일 기록 불일치
- writing-voice 검수에서 문단·사실·의료 경계·확신 강도·레퍼런스 제목·도입·흐름·마무리 장치·키워드 약속·고정 HTML 구성을 바꾸거나, 고칠 곳이 없는데 억지로 문장을 수정함
- writing-voice 검수에서 `directSubjectActionPurposeReviewed`, `vagueNounWrappersReviewed`, `softenedOrAbstractConclusionReviewed`, `userApprovedDirectVoiceExamplesApplied`, `directVoiceSentenceAuditCrossChecked` 가운데 하나라도 true가 아니거나, 직접화법 게이트가 잡은 문장이 있는데 `no-change-needed`로 통과시킴
