# 금손한의원 단일 글 공식

이 스킬은 위석부부한의원 정보글 한 편의 주제·내용과 편집 방식을 해석해 금손한의원 사실과 박준희 원장의 생활어로 다시 쓰는 정보 본문형만 작성한다. 완성 HTML의 유형 값은 `정보전달형`이다. 업체소개형·사례공유형·스토리텔링형·일상글·공지는 선택, 회전, 기본값, 대체 경로 어디에도 넣지 않는다.

## 레퍼런스와 금손 내용의 경계

- `wipark-content-briefs.json`: 직접 본문까지 검토한 위석 정보글 11편의 주제·독자 고민·핵심 일반 정보·정보 공개 순서
- `reference-master-profiles.json`: 같은 위석 원문의 기능적 내용 역할과 한 편 전체의 읽기 순서
- `reference-writing-intelligence.json`: 제목 장치의 독자 심리, 도입 설득, 전환, 디테일한 표현 기능, 신뢰 슬롯, 마무리 감정
- `goldhand-official-voice-profile.json`: 금손 공식 글 74편에서 분석한 박준희 원장의 화자 거리·질문 방식·종결어미·생활 장면·솔직한 연결
- `writing-voice-final-review-contract.json`: 완성 산문과 SEO 뒤 전체를 다시 듣고 표현만 국소 수정하며 사실·순서·의료 경계·레퍼런스 장치를 보존하는 마지막 검수
- `goldhand-naver-native-design-system.json`: 모든 글에 고정하는 모바일 문단과 네이버 순정 인용구·구분선·표1 디자인
- `clinic-facts.md`: 완성 원고에 넣을 금손한의원 사실·진료 원칙·사례의 내부 출처
- 권위 있는 외부 자료: 일반 질환·증상 설명에만 사용

한 글에서는 주제를 가져온 바로 그 위석 원문 한 편을 콘텐츠·편집 레퍼런스로 쓴다. 주제, 대표 고민, 핵심 일반 정보, 정보 공개 순서뿐 아니라 제목과 도입이 독자를 설득하는 이유, 문단 전환, 구체화 방식, 마무리 감정을 유지한다. 완성 문장은 원문을 복사하지 않고 금손 공식 74편 기준의 생활어로 새로 쓴다. 꾸밈은 원문과 무관하게 `goldhand-naver-native-v4`을 쓴다. 업체의 이름, 지역, 원장, 경력, 환자 수, 성과, 고유 프로그램, 치료 주장, 사례, 사진, 연락처는 모두 버리거나 확인된 금손 사실로만 교체한다.

## 포괄 키워드의 정보형 전환

`광주 한의원`, `광주 한의원 추천`처럼 질환이나 증상이 없는 메인키워드는 SEO 표기만 고정한다. 글의 실제 주제는 최근 3개와 의미가 겹치지 않는 `topicIdea`·`coverageQuestions`와 금손 사실 팩을 연결해 구체적으로 정한다.

- 허용: 통증이 치료 뒤 다시 불편해지는 생활 조건, 특정 동작에서 원인을 나눌 기준, 치료와 자가관리의 순서, 다른 검사가 먼저인 신호
- 허용: 추나요법·침·약침·골타·한약이 무엇을 위한 치료인지, 어떤 상태에서 고려하는지, 치료 전후 무엇을 확인하는지, 치료만 반복해도 변화가 더딜 수 있는 조건, 적용 한계와 다른 검사 우선 신호
- 금지: 한의원 고르는 법, 금손을 추천하는 이유, 잘하는 한의원의 조건, 시설·치료 종류 비교
- 증상·생활관리형 최소 정보 가치: 원인 또는 작동 이유 1개 이상, 독자가 관찰할 장면 2개 이상, 집에서 적용할 행동 1개 이상, 진료·검사 우선 경계 1개 이상
- 치료 정보형 최소 정보 가치: 치료 목적·원리, 적용 전 구분 기준, 고려할 상황, 효과가 더딜 수 있는 조건 또는 한계, 다른 검사·치료가 먼저인 경계. 자가관리는 해당 치료와 직접 관련 있을 때만 넣는다.

지역명·상호·운영정보를 본문에서 가렸을 때도 위 정보가 독립적으로 이해되어야 한다. 그렇지 않으면 정보전달형이 아니라 업체 선택형으로 보고 다시 작성한다.

치료 정보형도 치료명과 장점만 나열하지 않는다. 독자가 자신의 상태에 무조건 적용하게 만들지 말고, 금손의 실제 치료 설명과 진찰 후 선택 원칙을 사용한다. 치료가 많을수록 좋다는 결론, 특정 치료의 효과 보장, 다른 치료보다 우월하다는 비교는 쓰지 않는다.

## 필수 구조

### 1. 제목과 맞닿은 독자 고민 2~3개

- 선택 원문의 방식에 맞춰 도입부에 1개, 2개 또는 3개 둔다. 4개 이상은 허용하지 않는다.
- 독자가 검색 직전에 실제로 떠올릴 법한 서로 다른 고민이어야 한다.
- 첫 문장은 현재 겪는 증상·불편·망설임, 둘째 문장은 원인·치료 선택·검사·관리 중 다른 판단을 묻는 방식이 좋다.
- 세 번째가 있으면 앞의 두 고민에서 다루지 않은 별도의 판단 축을 맡긴다. 같은 뜻의 말바꾸기로 수만 늘리지 않는다.
- 실제 환자가 한 말이라고 주장하지 않는다. 확인된 직접 발화가 아니라 `대표적인 독자 고민`이다.
- HTML에서는 각각 `blockquote data-reference-role="reader-question" data-question-source="representative-reader-concern"`로 표시한다.
- 선택한 마스터가 인사 전 질문형이면 인용 2~3개를 인사 전에, 인사 후 질문형이면 고정 인사 뒤에 둔다.

### 2. 해결 방향 예고 1개

마지막 고민 뒤, 첫 정보 소제목 전에 자연스러운 산문 문단 하나를 둔다. 카드 제목이나 `해결책` 라벨을 만들지 않는다.

문단 안에서 다음 네 기능을 이어 쓴다.

1. 독자가 왜 헷갈리거나 망설이는지 구체적으로 짚는다.
2. 이번 글에서 설명할 범위를 정확히 밝힌다.
3. 금손한의원의 어떤 진료 기준·확인 방식으로 설명할지 필요한 만큼만 제시한다.
4. 읽고 나면 무엇을 구분하거나 판단할 수 있는지 알려 준다.

`오늘은`을 쓸 수 있지만 모든 글을 같은 문장으로 시작하지 않는다. `2분`, `3분`을 표면 문구로 복사하지 말고 구체적 숫자가 읽기 비용을 낮추고 주제별 보상이 읽을 이유를 만든다는 원리를 판단한다. 이 장치가 맞으면 실제 분량에 맞는 1~5분과 주제별 보상을 새로 쓰고, 맞지 않으면 선택 프로필의 대비·긴급 경계·모순·생활 손실 같은 다른 장치를 쓴다. HTML에서는 한 블록만 `data-reference-role="solution-preview" data-intro-persuasion-device="..." data-reader-payoff="..."`로 표시한다.

### 3. 금손한의원 소개 표 1개

독자 고민과 고정 인사는 편집 마스터가 정한 순서대로 모두 마치고, 완성된 `solution-preview` 직후에 `credential` 표를 정확히 한 번 둔다. 표의 제목은 `금손한의원 소개`, 내용은 `assets/goldhand-value-proof-library.json`의 고정 6행이며 주제에 따라 바꾸지 않는다.

`credential` 다음의 첫 콘텐츠 컴포넌트는 첫 정보 본문의 `divider` 또는 `section-heading`이다. 구분선과 소제목을 함께 쓰면 표를 첫 구분선 바로 앞에 둔다. `solution-preview`와 표 사이, 표와 첫 정보 본문 사이에는 이미지·일반 본문·`article-summary`·다른 표를 넣지 않는다. `data-preview-gap="true"`처럼 시각 간격만 만드는 요소는 콘텐츠로 보지 않는다. 이 배치는 모든 자동모드·정밀작성모드 글에 동일하게 적용한다.

### 4. 정보 본문

제목의 약속과 인용 고민들에 직접 답하는 2~4개 정보 덩어리로 전개한다.

- 증상이나 불편이 반복되는 이유
- 상태를 구분할 움직임·생활 장면·동반 신호
- 금손한의원에서 치료 방법을 고르는 기준과 설명 과정
- 집에서 무리 없이 살필 관리 기준
- 다른 검사나 의료기관의 평가를 먼저 생각해야 하는 상황
- 개인차와 치료의 한계

주제에 필요한 항목만 고른다. 침·약침·추나·골타·한약을 매 절마다 나열하지 않는다. `원인 → 구분 → 선택 이유 → 관리·한계`가 먼저다.

제목에 `2가지`, `3가지`가 있으면 실제 번호 답을 정확히 그 수만큼 둔다. 두 도입 인용의 개수와 본문 답의 개수는 별개다.

### 5. 회수와 레퍼런스별 마무리

- 선택 프로필의 `closingMechanism`이 요구하는 본문의 직접 답을 실제 명사로 다시 묶는다.
- 확인된 금손 경력이나 진료 태도가 주제와 맞으면 짧게 회수하고, 맞는 사실이 없으면 꾸미지 않는다.
- 안도·현실감·통제감·희망·감사 가운데 선택 레퍼런스가 만든 감정을 주제에 맞춰 남긴다.
- 누구에게나 같은 결과가 아님과 필요한 안전 경계는 구체적으로 밝히되 모든 글을 같은 중립 문장으로 끝내지 않는다.
- 강한 예약·내원 유도, 공포, 결과 보장은 쓰지 않는다.

## 마스터별 차이

정보형이라는 목적은 같지만 배치는 주제를 가져온 한 편을 따른다.

- `before-greeting`: 질문 2~3개 → 고정 인사 → 해결 방향 예고 → `credential` → 첫 정보 본문
- `after-greeting`: 고정 인사 → 질문 2~3개 → 해결 방향 예고 → `credential` → 첫 정보 본문
- 선행 이미지가 있는 마스터: 관련 금손 공식 이미지가 있을 때만 같은 위치에 둔다.
- 지식 공백 문단이 있는 마스터: 왜 잘못 알고 있는지를 해결 방향 예고 안에 자연스럽게 합친다.
- 외부 마스터에 증명 표가 있어도 그 슬롯은 고정 `credential`의 위치·문구·개수를 통제하지 않는다. 별도 증명 표를 추가하지 않고 모든 글에 같은 고정 6행 `credential` 한 개만 둔다.

질문 2~3개, 해결 방향 예고, 정보 본문을 사용하되 핵심 내용과 정보 순서, 제목·도입·전환·마무리 기능은 선택한 콘텐츠·편집 레퍼런스에 맞춘다. 금손 공식 프로필은 이 기능을 유지한 채 문장을 실제 진료실 생활어로 자연화한다. SEO까지 반영된 완성 산문은 writing-voice 최종 재청취로 generic한 연결·평평한 리듬·독자 초점 이탈·근거 없는 윤색만 고치며, 내용과 구조는 바꾸지 않는다. `credential`은 완성된 해결 방향 예고 뒤이자 첫 정보 본문 앞에 고정한다.

## 모바일 가독성 공식

- 일반 본문 한 묶음은 모바일 시각 줄 2개 또는 3개다.
- 각 줄은 한 가지 의미가 자연스럽게 이어지도록 나누며 공백 제외 4~24자 안에 둔다.
- 한 묶음 뒤에는 반드시 빈 줄을 둔다.
- 긴 설명은 4줄짜리 한 문단으로 두지 않고 2~3줄 묶음 여러 개로 나눈다.
- 고정 인사, 독자 질문, 소제목, 표 셀, 연락처는 이 줄 수 검사에서 제외한다.
- HTML은 일반 문단에 `data-mobile-group="true"`, 뒤 빈 줄에 `data-preview-gap="true"`를 둔다.

## 사실 팩

초안 전에 내부적으로 다음만 적는다.

- 정확 메인키워드와 확정 제목
- 선택한 주제 출처 ID·`semanticTopicId`·핵심 대상·검색 의도
- 선택한 콘텐츠 레퍼런스 ID·URL 한 개와 핵심 정보 순서
- 선택 주제의 의미 서명, 실제로 답할 질문, 별도 확인한 의학 근거
- 서로 다른 독자 고민 2~3개
- 해결 방향 예고의 혼란 원인·설명 범위·금손 근거·독자 판단
- 제목의 직접 답 1~4개
- 사용할 금손한의원 사실과 원장 직접 경험
- 일반 의학 설명, 예외, 다른 기관 우선 신호
- 집에서 할 수 있는 관리
- 금지할 주장·수치·표현
- 정확 키워드를 자연스럽게 넣을 서로 다른 본문 역할 2~3개
- 이미지가 실제로 보완할 문단

대응할 금손 사실이 없으면 원문 사실이나 가상 사례로 채우지 않는다. 주제를 바꾸거나 발행에 꼭 필요한 누락값 하나만 묻는다.

## 금손한의원 목소리 — 유일한 말투 기준

- `안녕하세요, 금손한의원 박준희 원장입니다.`를 정확히 한 번 쓴다.
- 환자 한 명에게 설명하듯 구체적인 신체 장면과 판단 기준을 사용한다.
- 짧은 결론문과 이유를 풀어 주는 긴 문장을 섞는다.
- `중요합니다`, `도움이 됩니다`, `살펴봐야 합니다`만 반복하지 않는다.
- `판단 기준`, `생활의 흐름`, `먼저 볼 기록`, `확인할 순서` 같은 추상 명사를 실제 독자의 보통말보다 우선하지 않는다.
- `ㅎㅎ`, `ㅠㅠ`, `^^`, 하트, 이모지로 친근함을 만들지 않는다. 직접 질문, 1인칭 판단, 생활 장면으로 온도를 만든다.
- `references/goldhand-official-voice.md`와 `validate_goldhand_voice.py`를 통과하지 못한 원고는 발행하지 않는다.
- `살이 안 빠진다`, `왜 그럴까요?`처럼 흔하고 자연스러운 표현은 표절 회피를 이유로 어색하게 치환하지 않는다.
